# 最低生产条件启动零丢包与诊断日志时间窗导出

## 1. 任务目标

本任务一次解决两个独立但需要共同进入下一轮实机验证的问题：

1. **P0：修复最低生产条件每轮采集开始时稳定出现的固定丢失。**
2. **诊断日志重构：保证采集期间日志持续、及时落盘，并把导出方式从“选择某个进程 run”改为“选择时间段，跨 run 导出该时间段对应记录”。**

下一轮实机测试的首要生产锚点为：

```text
4 cards
trigger = 40 Hz
acqTime = 20000 ns
sampleInterval = 4 ns
A+B
32 bit/channel
realtime imaging = ON
imaging block = 200 Aline
```

验收目标不是“启动后很快稳定”，而是：

> 从每轮第一个定义为生产有效的 hardware trigger 开始，四卡所有 UDP packet / Aline 都必须完整；不得用 warm-up 丢弃前几帧来规避问题。

本任务**不处理 P1：40 Hz / 50 us 即使仅采集也出现大量丢失的问题**。P1 留待下一轮拿到可靠时间窗日志后继续分析。

## 3. P0 已知证据与当前代码缺陷

实机已观察到：

```text
40 Hz / 20 us / 200 Aline / realtime imaging ON

每轮采集开始：稳定出现少量、约数次丢失
随后稳态：前端长期不再出现丢失
```

该形态优先指向 measurement-session 边界状态缺陷，而不是稳态吞吐不足。

当前代码至少存在以下确定性风险：

### 3.1 Start command 与 DataProcessor gate 顺序竞态

当前 MainWindow 启动路径等价于：

```text
sendStartMeasure()
-> FPGA 可以立即开始发 UDP
-> sendStartMeasure() 返回
-> setMeasureEnabled(true)
```

而 DataProcessor 对 `m_measureEnabled == false` 的包会成功 dequeue 后直接跳过，不进入组包。

因此存在明确窗口：

```text
hardware 已开始发送
但 processor 仍未 armed
```

首 trigger 的前部 packet 可被程序主动丢弃。

### 3.2 Session 状态跨轮残留

当前 `setMeasureEnabled(bool)` 只改变一个 atomic gate；DataProcessor worker 内的 `PacketAssemblyBuffer` 与以下状态跨 Start/Stop 生命周期持续存在：

```text
m_lastFlushedTriggerSeq
m_hasFlushedOnce
m_consecutiveDiscards
PacketAssemblyBuffer current partial trigger
input queue 中的旧 session packet
raw-order sequence anchor
```

下一轮首 trigger 因此可能同时受到旧 partial assembly、旧 trigger anchor 与当前首包被 gate 丢弃的影响。

### 3.3 MainWindow 状态与实际 command outcome 不严格一致

当前 start send 失败后仍可能继续把 UI/internal state 标成 measuring 并打开 gate。零丢包生产路径不允许这种静默状态漂移。

## 4. P0 必须实现的 Session Lifecycle 语义

允许 Codex 选择具体类设计，但最终行为必须满足以下语义；不得仅做“把 `setMeasureEnabled(true)` 提前一行”这种局部补丁。

### 4.1 单一所有者

measurement session 的 arm/start/stop/disarm 生命周期必须由 `NetworkController` 或等价的单一控制层统一拥有。

`MainWindow` 不得再直接负责 DataProcessor gate 的时序正确性。

Direct start 与“等待 ready/config ack 后延迟执行”的 queued start 必须经过**同一条实际 start transaction**，不得一条修好、一条保留旧竞态。

### 4.2 Start transaction

实际发送 hardware Start Measure 前必须按以下逻辑完成：

```text
DISARMED
  -> PREPARING
  -> 所有 DataProcessor 完成本轮 session reset
  -> 所有 DataProcessor 明确 ARMED
  -> 才允许向任何采集卡发送 Start Measure
  -> 4/4 本地 sendto 成功
  -> RUNNING
```

必须满足：

1. reset/prepare 必须在 DataProcessor 自己的 worker/thread ownership 下完成，或通过等价的线程安全 barrier 完成；不得从 GUI thread 并发直接修改 worker 正在使用的 `PacketAssemblyBuffer`。
2. prepare 期间 measure gate 必须关闭。
3. prepare 必须清除**上一 session 的处理状态**，至少包括：
   - 当前 partial `PacketAssemblyBuffer`；
   - `m_lastFlushedTriggerSeq`；
   - `m_hasFlushedOnce`；
   - `m_consecutiveDiscards`；
   - 已经排队、但属于上一 session / gate-off 时段的 input queue packet。
4. 上述 session reset 属于生命周期边界，不得把被清理的旧 partial 计成当前 session 的 `packetsDropped` / `triggersPartial`，不得 emit 假 `partialTrigger`。
5. raw receive order 的 session anchor 必须有明确 reset 语义，避免新一轮第一个 trigger 与上一轮最后一个 trigger 做跨 session raw-gap 比较。允许为 `CardStats` 增加小型 `resetRawSequenceAnchor()` 或等价机制，但不得改变 `observeRawReceive()` 的正常包判断算法。
6. 所有 processor prepare/arm 必须有 bounded timeout；任一失败或超时，**禁止发送 hardware Start Measure**。
7. processor 全部 armed 之后，才调用实际 `doSendStartMeasure()`。
8. 四卡生产模式下，Start command transaction 只有 `4/4 sendto` 成功才算 start 成功。若出现部分成功，必须：
   - 记录 partial-start failure；
   - 对全部目标卡执行 best-effort Stop Measure rollback；
   - disarm/reset 本轮 session；
   - 不得静默进入 measuring state。
9. 不要求为 Start Measure 新增 FPGA ACK 协议；本任务只要求把现有“本地 sendto 成功”语义做到四卡一致并事务化。

### 4.3 Stop / next-start boundary

Stop 时必须保证：

1. 正常 RUNNING 状态先发送 hardware Stop Measure，再进入 disarm/reset；
2. stop 后 trailing/late packet 不得成为下一轮 session 的 assembly/sequence anchor；
3. 下一轮 Start 必须再次经过完整 PREPARING -> ARMED barrier；
4. session boundary 清理不得制造伪 `packetsDropped` / `triggersPartial`；
5. stop command 本地发送失败时不得静默宣称已完全停止；必须记录明确 failure/rollback 状态。

不要求通过 sleep/warm-up 固定等待若干 trigger；禁止用“丢弃前 N 个 trigger”掩盖问题。

### 4.4 统计语义

现有全局累积计数：

```text
socketPacketsReceived
processorPacketsDequeued
packetsDropped
triggersComplete
triggersPartial
batchBoundaryDiscards
raw-order / assembly observability counters
```

默认保持 cumulative，不得为了修启动问题直接每轮清零。

本轮是否零丢包由 session start/stop marker 对应的 counter delta 与 partial-trigger 记录判断。

现有 full-trigger gap 推断算法本任务不做泛化重写；只通过明确 session reset 防止跨 session triggerSeq 被误认为同一连续采集窗口。

## 6. 日志持久化目标

当前 `DiagnosticRecorder` 已经：

- 使用独立 worker thread；
- 事件进入 bounded queue；
- 持久化到 `runtime.log` / `events.jsonl` / `network_history.jsonl` / `settings_history.jsonl` / `card_history.jsonl`；
- 正常情况下最多约 1 s 做一次 timed flush；
- 支持显式 `requestFlush()` / bounded `flush()`。

本任务不得退化成“只在用户点击导出时才把内存日志写磁盘”。

### 6.1 Active acquisition 持续落盘

必须继续保持 worker 异步写盘，并满足：

1. active acquisition 期间普通日志持续 append 到持久文件；
2. 正常 worker flush 周期不得比当前 1 s 更差；
3. `measurement_started` 记录入队后立即 `requestFlush()`；
4. `measurement_stopped`、start rollback、stop failure 等 session boundary 记录后立即 `requestFlush()`；
5. 每轮 stop 完成后，必须保证 session 末尾日志最终可以通过 bounded flush 落盘；该 barrier 不得长期阻塞 receiver hot path，也不得在 `recvfrom()` / DataProcessor packet hot path 做同步磁盘 I/O；
6. 程序异常退出时，已经成功 flush 的记录必须仍可作为 incomplete run 被枚举和导出。

### 6.2 Start/Stop 边界快照

每个 session 的 start 与 stop/rollback 附近必须主动记录/刷新：

- 当前 settings/config snapshot；
- 四卡 cumulative runtime counter snapshot；
- 当前 runtime_ingress / interface snapshot（已有网络入口观测能力）；
- session ID 关联字段。

目的：后续选择一个时间窗时可以直接计算该轮采集的 counter delta，不依赖用户记忆“这是哪个 run”。

不得把这类快照改成每 packet / 每 trigger 写盘。

## 7. 导出逻辑改为“按时间段跨 run 导出”

### 7.1 UI 行为

`DiagnosticExportDialog` 不再要求用户先选择：

```text
当前运行 / 某个历史运行
```

改为至少提供：

```text
开始时间
结束时间
现场说明（保留）
ZIP 保存路径（保留）
```

时间控件必须：

- 使用本机 local time，显示到秒；
- 可人工编辑；
- 校验 `start <= end`；
- 结束时间不得默认为未来时间；
- 显示 diagnostics retention 中当前可用的最早/最晚覆盖时间，避免用户盲选。

默认时间窗可由 Codex 选择合理值（例如最近一段时间），但不得改变“用户可明确指定任意保留区间”的核心行为。

除该诊断导出 dialog 外，本任务不得重做主采集 UI；现有卡状态栏、成像 UI 等保持不变。

### 7.2 跨 run 选择

时间段导出必须扫描 diagnostics retention 下**所有与所选时间窗有重叠的 run directory**，包括：

```text
正常结束 run
当前 active run
异常退出 / incomplete run
```

不得因为用户当前进程 run 与实验 run 不同，就导出一个仅有初始化事件的新 run。

### 7.3 时间过滤语义

正式窗口定义为：

```text
[startTime, endTime]
```

事件类记录：

```text
events.jsonl / runtime.log
```

只导出时间戳位于正式窗口内的记录。

对于需要计算 counter delta / 配置上下文的历史流：

```text
network_history
settings_history
card_history
```

除窗口内所有记录外，还必须尽可能保留：

```text
最后一条 timestamp <= startTime 的 boundary-before context
第一条 timestamp >= endTime 的 boundary-after context
```

这些窗口外 context 必须在 manifest 或独立 context 文件中明确标记，不得让分析者误认为它们属于正式时间窗事件。

这样后续可以准确得到：

```text
窗口前 counter baseline
窗口内变化
窗口后 final counter
```

### 7.4 Active run immutable boundary

如果导出时间窗覆盖当前 active run：

1. 点击“导出”时捕获 immutable export boundary；
2. exporter worker 对该 boundary 做必要 flush；
3. 后续新产生的日志不得因为 exporter 执行较慢而越过点击时边界混入本次导出；
4. 最终仍必须再按用户 start/end 时间过滤。

### 7.5 Export output / manifest

保留现有 ZIP 诊断结构可读性，并至少在 `manifest.json` 或等价 metadata 中加入：

```text
requestedStartTime
requestedEndTime
exportCapturedAt
sourceRunIds[]
sourceRunCount
formalWindowRecordCounts
boundaryContextCounts
actualEarliestIncludedTime
actualLatestIncludedTime
active/incomplete source flags
missingFiles[]
truncationReasons[]
recorder drop/write-error state
```

`summary.txt` 顶部必须明确显示“本 ZIP 为时间窗导出”，以及用户选定的开始/结束时间。

如果时间窗没有任何正式记录，UI 必须给出明确“该时间段没有日志”结果，不得生成一个看似成功、实际只包含当前空 run 初始化信息的 ZIP。

### 7.6 实现性能要求

导出工作必须继续在后台线程执行；不得在 UI thread 同步扫描数百 MB diagnostics 文件。

对 `.jsonl` 历史文件优先逐行/stream filter，不得无条件把所有 retained run 的完整历史一次性全部载入内存。

现有 retention policy 默认保持：

```text
maxRetainedRuns = 30
maxRetainedBytes = 500 MB
```

本任务不调整 retention 数值。
