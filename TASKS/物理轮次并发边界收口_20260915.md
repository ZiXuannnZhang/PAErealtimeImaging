# 1. 当前审查发现

## 1.1 已通过，禁止回退

以下行为已经通过源码/测试审查，本任务必须视为回归基线：

```text
roundGeneration file rollover
manual save partial-timeout split
count-complete file split
triggersPerFile < N / > N
saver FIFO/backlog ordering
TimeoutBoundary UI counter reset
CountBoundary final reconstruction frame timing
saving lifecycle physical-round state reset
```

不要重新设计这些主体逻辑。

## 1.2 Blocker A：auto-save generation 仍受 UI event-loop 时序支配

当前生产路径中，HostOutput 在 logical scan 入保存队列前读取 save session generation；而 TimeoutBoundary 事件发生在 network/source thread，MainWindow 需要通过 `QMetaObject::invokeMethod` marshal 回 UI thread 执行 `advanceAutoSession()`。

因此存在合法竞态：

```text
idle > timeout
→ next control arrives
→ normalizer emits TimeoutBoundary + roundGeneration++
→ MainWindow queues advanceAutoSession() to UI thread
→ UI callback has not run yet
→ first new-round LogicalScan arrives
→ captureSaveSessionGen() still reads old session generation
```

此时 TriggerGroup 可能变成：

```text
roundGeneration = NEW
sessionGen       = OLD
```

上一轮整改已经保证 FileSaver 会因为 `roundGeneration` 变化切新文件，但 auto-save directory routing 仍可能把新 round 的首批文件放进旧目录；等 UI 稍后推进 generation 后，同一 physical round 后续数据又进入新目录。

这属于生产数据组织错误，必须关闭。

### 当前测试缺口

上一轮 auto-save fixture 是先手工把 generation 改成新值，再送 next round 数据，等价于假设 UI callback 已经完成；它没有模拟：

```text
boundary source thread
→ UI callback delayed
→ next LogicalScan races ahead
```

所以现有 T5 PASS 不足以证明生产 auto-save race 已关闭。

## 1.3 Blocker B：stale cutoff 不得继续使用“尝试提交次数”冒充 ImagingSvc snapshot 序号

当前 `RingRoundUiState` 的 stale cutoff 基于 producer-side submission count；现有调用顺序中，计数发生在真实 `submitRingBlock()` 成功确认之前，因此 failed submit 会扩大 cutoff。

更重要的是，当前源码中：

- `ImagingController::submitRingBlock()` 在写共享内存并准备 `ring_block_ready` 后调用 `sendCommand()`；
- `sendCommand()` 是 `void`；
- ZMQ 使用 `dontwait`；
- send exception 当前被静默吞掉。

因此仅仅把 `recordSubmit()` 移到 `submitRingBlock() == true` 后面，也不能自动证明：

```text
producer successful submit count == ImagingSvc frame_seq
```

本任务必须解决“身份域不一致”，不能只机械移动一行计数。

# 3. Auto-save generation：从 UI 状态改为同步数据面/业务边界状态

## 3.1 核心要求

`m_autoSaveNext` / UI callback 不得继续成为 TimeoutBoundary 后 next logical group 使用哪个 `sessionGen` 的唯一权威来源。

需要建立一个线程安全、低频、可幂等的 auto-save round coordinator，名称不限，例如：

```text
AutoSaveRoundCoordinator
PhysicalRoundSaveSessionCoordinator
```

它的职责只包括：

```text
current save session generation
physical round → save generation binding
next directory path binding / registration state
boundary idempotency
```

不要把 FileSaver 写盘、normalizer 分类或 UI 渲染搬进该 helper。

## 3.2 TimeoutBoundary 的同步提交顺序

对于 auto-save enabled 的 TimeoutBoundary，推荐并要求满足下面的 publish ordering：

```text
1. derive/reserve next save generation
2. prepare/register generation → directory mapping
3. commit/publish NEW save generation atomically/thread-safely
4. boundary callback returns
5. later NEW round LogicalScan reads committed NEW generation
6. UI thread asynchronously updates labels/PNG target/diagnostics
```

关键点：

> **先准备 mapping，再发布 generation。**

禁止：

```text
publish NEW generation
→ directory mapping 尚未注册
→ FileSaver resolver 暂时找不到目录
```

也禁止：

```text
先把 UI callback 排队
→ 期望 UI thread 未来某时再推进 generation
```

## 3.3 `captureSaveSessionGen()` 必须读取同步 coordinator

new round group 的 save generation capture 必须来自 thread-safe committed state，而不是直接读取仅由 UI thread 修改的成员。

允许实现形式包括：

```text
atomic generation + mutex protected directory registry
shared immutable mapping snapshot
network/controller-owned save generation state
```

但必须证明：

```text
TimeoutBoundary callback 返回后
next LogicalScan captureSaveSessionGen() == NEW generation
```

## 3.4 UI `advanceAutoSession()` 角色调整

现有 `advanceAutoSession()` 可以保留 UI/目录显示职责，但不得在 timeout 路径上独立、再次推进 generation。

建议拆成：

```text
reserve/commit generation      // thread-safe authoritative
apply generation to UI/PNG     // UI-thread presentation side effect
```

UI callback 应消费“已经决定的新 generation”，而不是再次执行 `++generation`。

必须避免：

```text
network boundary advances once
+ timeout timer advances once
+ UI callback advances once
= generation jump / empty directory
```

幂等 key 至少应包含：

```text
measurementSession
roundGeneration
boundaryKind
```

或提供等价的 generation-monotonic proof。

## 3.5 CountBoundary 不得被顺手改坏

本任务主要修 TimeoutBoundary race。

当前 CountBoundary 的 auto-save / PNG / final-frame 时序已经通过实机和审查，不允许为了“统一实现”简单把 generation advance 前移到 normalizer CountBoundary 事件时刻。

如果你选择统一 coordinator：

- CountBoundary 可以记录 pending next generation；
- 但真正 publish 时点必须继续保证上一轮 final reconstruction frame/PNG 不会进入 next round directory；
- 必须用测试证明与当前行为等价或更严格。

如果没有必要，CountBoundary 路径保持原语义更安全。

## 3.6 Directory preparation failure

如果 NEW generation 对应目录无法创建/注册：

禁止静默 fallback 到 OLD directory。

允许策略：

```text
stop/disable auto-save for NEW round
emit explicit diagnostic/error
continue acquisition/imaging if安全
```

或者在保存侧安全等待 mapping ready。

无论采用哪种方式，都必须保证：

```text
NEW round data never silently lands in OLD auto-save directory
```

# 4. Stale snapshot cutoff：统一 identity domain

## 4.1 禁止继续使用 attempt count

以下模式不再接受：

```text
recordSubmit() before submitRingBlock()
cutoff = attemptedSubmissions
compare ring_snapshot_ready.seq(frame_seq) <= cutoff
```

原因：两边不是同一计数语义。

## 4.2 “仅在 submitRingBlock()==true 后计数”只是最低门槛，不是自动完成

如果继续采用 successful-submit count → `frame_seq` 映射，Codex 必须首先证明：

```text
submitRingBlock true
⇔ corresponding ring_block_ready successfully queued/sent
⇔ ImagingSvc eventually processes one block
⇔ exactly one frame_seq increment
```

当前源码的 `sendCommand(void)` + `dontwait` + silent failure 已经使这个等价关系**不能直接成立**。

因此不得只做：

```text
if (submitRingBlock(...)) recordSubmit();
```

然后宣称问题解决。

## 4.3 推荐方案：沿用已有 `submit_index`，让 stale admission 在同一 identity domain 比较

当前 producer 的 `ring_block_ready` 已携带：

```text
submit_index
```

推荐最小而严格的方案：

```text
producer submit_index
    ↓ ring_block_ready
ImagingSvc processRingPulse(..., submitIndex, ...)
    ↓
ring_snapshot_ready echoes origin submit_index
    ↓
MainWindow / RingRoundUiState stale admission compares submit_index
```

这样 cutoff 可以定义为：

```text
lastPreBoundarySubmitIndex
```

判断：

```text
snapshot.submit_index <= cutoff  → OLD/stale
snapshot.submit_index >  cutoff  → NEW/admit
```

该方案的优势：

- producer gap 不影响正确性；
- failed send 不会产生 snapshot；
- new round submit index 单调增加，天然大于 pre-boundary cutoff；
- 不再要求 producer submission count 与 ImagingSvc `frame_seq` 数值相等。

`frame_seq` 可继续作为显示/诊断序号，不要再把它冒充 producer submit identity。

## 4.4 如果不用 submit_index echo

允许其它实现，但必须在报告中给出严格证明。

例如：

```text
make sendCommand return definitive enqueue result
submitRingBlock return actual ready-message enqueue success
count only successful ready messages
prove one ready message → one frame_seq increment before reset
```

如果做不到该证明，必须采用更强 identity/ack 方案，不能靠“当前一般不会 send 失败”接受。

## 4.5 Ring reset ordering / ack

审查 reset 与 ready message 的顺序。

如果 stale cutoff 的正确性依赖：

```text
all OLD ring_block_ready
→ ring_reset
→ all NEW ring_block_ready
```

则必须证明同一 socket/mutex 下成功发送的消息顺序满足该要求。

若无法在主端单方面证明 reset 已被 ImagingSvc 处理，可增加最小 control-plane ack，例如：

```text
ring_reset_ack
boundary_submit_index
svc frame_seq (diagnostic only)
```

允许为此对 `ImagingController` / `ImagingSvc` 做**最小消息元数据修改**。

禁止修改 Ring CUDA 数值重建、滤波、几何参数、重建算法。

## 4.6 Lifecycle / epoch

如果 `submit_index` 或 snapshot identity 在以下生命周期会归零：

```text
ImagingSvc restart
start/stop imaging
measurement session restart
ring reconfigure
```

stale guard 必须一起 reset 或带 session/epoch。

不能让上一生命周期 cutoff 把新服务会话前几帧误判 stale。



## A2. Saver backlog + UI delayed

```text

```

- old backlog 全部写 old directory；
- new groups 全部写 new directory；
- 同一 physical round 不跨两个 auto directory；
- FileSaver roundGeneration rollover 仍正确。

## A3. Exactly-once generation advance

```text
PhysicalRoundEvent observer

```

不得出现：

```text
+2 generation
空目录
目录跳号
```

## A4. CountBoundary regression

确认正常完整 round：

- final old-round reconstruction frame 仍被接收；
- old PNG/save 仍属于 old generation；
- next round generation 只推进一次；

## A5. Directory registration failure

注入 `mkdir/register` 失败。

必须证明：

- NEW round 不 fallback 到 OLD directory；

## A6. Lifecycle

覆盖：

```text

```

新会话不得继承旧 round → session binding。

# 6. Required Tests — stale cutoff / identity

## B1. failed local submit 不扩大 cutoff

构造：

```text
successful OLD submit
failed OLD submit
successful OLD submit
TimeoutBoundary
NEW submit
```

断言 NEW snapshot 不会因为 failed submit 占了计数位而被误丢。

## B2. ZMQ send failure / gap


## B3. delayed OLD snapshot after timeout

断言：


## B4. immediate NEW snapshot after timeout

紧跟在 B3 后送 NEW round snapshot。

断言它立即 admitted；不得因为 cutoff 数值过大被一起丢掉。

## B5. multiple OLD delayed snapshots + first NEW frame

