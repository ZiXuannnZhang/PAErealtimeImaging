# 崩溃调查报告：实时成像环形帧转换 use-after-free

**崩溃时间**：2026-08-11 01:17:16
**程序**：MC410T_Receiver.exe（Debug 构建）
**崩溃线程**：38668（0x970C）
**异常**：0xC0000005 读访问违例
**结论**：环形扫描实时成像中，帧数据 `QVector<float>` 的底层存储在工作线程仍持有引用时被释放，`ImagingController::frameDataToImage()` 读取悬垂指针导致崩溃。已按“单飞行 + 可汇合 + 队列投递”方向修复并重新构建。

## 3. 崩溃点定位

### 3.1 反汇编

崩溃指令位于 `MC410T_Receiver.exe+0x674A5`：

```asm
14006748b: mov    -0x14(%rbp),%eax      ; y = 460
14006748e: imul   0x38(%rbp),%eax       ; index = y * nx
140067492: mov    -0x18(%rbp),%edx      ; x = 1687
140067495: add    %edx,%eax             ; index = 1657687 (0x194B57)
140067497: cltq
140067499: mov    0x30(%rbp),%rcx       ; rcx = &data（QList<float>*）
14006749d: mov    %rax,%rdx
1400674a0: call   1401de7d0 <QList<float>::at(qsizetype) const>
1400674a5: movss  (%rax),%xmm0          ; <-- 崩溃：读取 RAX 指向的内存
```

所属函数（带源码交错确认）：

```cpp
QImage ImagingController::frameDataToImage(const QVector<float> &data, int nx, int ny) const
{
    if (data.size() < nx * ny) return QImage();
    float minV = 1e30f, maxV = -1e30f;
    for (int i = 0; i < nx * ny; ++i) { float v = data[i]; ... }   // 极值循环：已完整跑完
    ...
    for (int y = 0; y < ny; ++y) {
        uchar *line = img.scanLine(ny - 1 - y);
        for (int x = 0; x < nx; ++x) {
            float t = (data[y * nx + x] - minV) / range;   // <-- 崩溃位置
            ...
        }
    }
}
```

（Qt 6 中 `QVector<float>` 是 `QList<float>` 的别名，符号为 `_ZNK5QListIfEixEx`。）

### 3.2 崩溃现场寄存器与循环状态

| 寄存器 | 值 | 含义 |
|---|---|---|
| RIP | 0x7FF732E074A5 | 崩溃指令 |
| RAX | 0x2A7167982D0 | `QList::at()` 返回的数据指针（悬垂） |
| RCX | 0x37D7BFF9B0 | `&data`，即工作线程栈上 wl1 对象 |
| RSP | 0x37D7BFF8B0 | 崩溃时刻栈指针 |
| RBP | 0x37D7BFF930 | frameDataToImage 帧基址 |
| 帧内 y / x | 460 / 1687 | 崩溃循环进度，index = 1,657,687 |
| 帧内 nx / ny | 3600 / 3600 | 10μm 网格参数 |
| 帧内 minV / maxV | -6063.69 / 7123.68 | 极值循环读到了真实数据 |

### 3.3 调用链（由 minidump 栈内存还原）

```
ntdll/系统线程入口
  -> libstdc++ execute_native_thread_routine
    -> std::thread::_State_impl::_M_run            (exe+0x680C2)
      -> _Invoker::operator()                        (exe+0x680E6)
        -> _M_invoke -> __invoke -> __invoke_impl   (返回地址 exe+0x681D4)
          -> processRingMessage 工作线程 lambda      (exe+0x60F32)
            -> emit ringImageReady(frameDataToImage(wl2...),   // 第一实参，先执行，正常返回
                                   frameDataToImage(wl1...),   // 第二实参，崩溃
                                   seq)
              -> ImagingController::frameDataToImage (exe+0x611D2 调用，返回地址 exe+0x611D7)
                -> QList<float>::at()                (exe+0x1DE7D0)
                  -> movss (%rax),%xmm0  <-- 崩溃
```

注意：GCC 对函数实参按从右到左求值，**崩溃的是 `frameDataToImage(wl1)`**，不是源码顺序上的第一个参数。

### 3.4 悬垂指针反推

Qt 6.8 `QArrayDataPointer{d, ptr, size}`（24 字节 QList 对象）：

- `QList::data()` 返回 `[对象+8]`（ptr 成员）
- `QList::at(i)` 返回 `ptr + 4*i`

由 `RAX = 0x2A7167982D0`、`index = 1,657,687` 反推崩溃时刻 `wl1.ptr = 0x2A7167982D0 - 4×1,657,687 = 0x2A716145574`，即一块**已被释放/部分取消提交的堆内存**。极值循环读取该块仍映射的页面（数据残存，minV/maxV 为真实值），像素循环读取到未提交页面时触发访问违例。

## 4. 根因分析

**结论：环形帧 `QVector` 存储的 use-after-free。**

工作线程在 `processRingMessage` 中：

```cpp
QVector<float> wl1(frameSize), wl2(frameSize);
... memcpy 从共享内存取帧 ...
{ QMutexLocker l(&m_ringFrameMutex); m_latestRingFrames[0] = wl1; m_latestRingFrames[1] = wl2; }
emit ringImageReady(frameDataToImage(wl1, nx, ny), frameDataToImage(wl2, nx, ny), seq);
```

wl1/wl2 与 `m_latestRingFrames`、UI 侧 `latestRingFrame()` 拷贝共享同一底层存储（引用计数）。原实现存在以下结构性问题，共同导致存储被提前释放/内存压力失控：

1. **`std::thread(...).detach()`**：工作线程无归属、无汇合、无并发上限。帧率高于处理速度时 worker 无限叠加，每个 worker 瞬时占用约 103MB（wl1+wl2）+ 2×13MB QImage；多次崩溃中已出现 Qt “Out of memory”（c0000602）。
2. **裸线程捕获 `this` 并直接 emit Qt 信号**：跨线程信号发射 + 与 `finishStopSvc`/析构的生命周期竞态。
3. **`finishStopSvc` 5 秒超时**：超时后照样删除共享内存/ZMQ，迟到的 worker 会访问已释放资源。

### 4.1 转储中的一处矛盾（如实说明）

转储捕获到的栈上 wl1 QList 对象是完整有效的 `{d=0x1C7B779A040, ptr=0x1C7B779A050, size=12,960,000}`，与崩溃时刻 `at()` 返回的悬垂指针（0x2A7167982D0）不一致。异常派发/转储捕获过程中该栈槽被改写，或 dbghelp 捕获线程栈与异常上下文的时刻存在偏差（线程列表上下文普遍带 48 字节零前缀、大小 1663，本身就是异常迹象）。因此**无法仅凭这份转储把具体是哪一个引用计数/所有权环节写死**；但崩溃路径（环形帧转换读取悬垂指针）与 use-after-free 性质确定，且该代码路径的结构性缺陷足以稳定诱发崩溃。

## 5. 修复内容

### 改动文件

- `MC_410T_MultiCard/delivery/include/ImagingController.h`
- `MC_410T_MultiCard/delivery/src/ImagingController.cpp`

### 修复点

1. **detach 改为可汇合**：`m_ringWorker`（`std::thread` 成员）持有工作线程；`finishStopSvc()` 先置 `m_running=false`，再**无条件 `join()`**，最后才释放共享内存/ZMQ（删除 5 秒超时放行）；析构函数兜底再 join 一次。
2. **单飞行限流**：`m_ringWorkerBusy` 原子标志保证同一时刻至多一个转换 worker；处理期间到达的新帧只记录 `m_ringFramePending + m_ringPendingSeq`（“最新一帧待处理”），当前帧完成后经 UI 线程事件循环继续处理最新帧。内存占用被限制在约 1~2 帧，杜绝 worker 无限叠加。
3. **不再从裸线程直接 emit**：工作线程完成 QImage 转换后，用 `QMetaObject::invokeMethod(this, ..., Qt::QueuedConnection)` 把结果（QImage 按值捕获，隐式共享）投递到 UI 线程，由 UI 线程执行 `emit ringImageReady(...)`。
4. 头文件移除旧的 `m_ringFrameWorkers / m_ringFrameDoneMutex / m_ringFrameDoneCv`，新增 `startRingFrameWorker(int seq)`。

已重新构建：`delivery/build/mingw_debug/bin/MC410T_Receiver.exe`（构建成功）。

## 6. 本次改动可能带来的新风险

1. **停止/析构时 UI 短暂阻塞**：`finishStopSvc()` 现在无条件 join，若恰逢 3600² 帧转换中，UI 线程最多等待一帧转换时间（秒级）。这是用“停止稍慢”换“不再崩溃”的取舍；若后续需要，可把停止也改为异步等待。
2. **高帧率下中间帧被合并**：单飞行 + “最新一帧待处理”意味着饱和时中间帧会被跳过（实时预览无影响）；若依赖“每帧都存 PNG”，保存的帧数可能少于发送帧数。如业务要求逐帧保存，可后续改为“有界队列 + 逐帧保存”并接受更高内存。
3. **ringImageReady 变为 UI 线程直接连接**：原 emit 在 worker 线程（AutoConnection 排队到 UI），现在在 UI 线程直接执行槽，槽内 `showRingImage()` 降采样仍占用 UI 时间——与原行为一致（本来就在 UI 线程跑），但若槽内再引入耗时操作需注意。
4. **队列事件中的 QImage 生命周期**：`invokeMethod` 投递的 lambda 按值持有两张 QImage；若 UI 事件循环长时间阻塞，已投递事件会暂存（每事件约 26MB 引用计数开销的共享数据，受单飞行限制数量有限）。
5. **seq 偶发回退/重复**：`m_ringFramePending` 与 `m_ringPendingSeq` 的写入顺序在极端时序下可能让显示帧号短暂回退或重复，仅影响状态栏计数显示，不影响数据正确性。
6. **防御性 join**：`startRingFrameWorker()` 中若上一线程尚未完全退出会短暂阻塞（微秒级），不会死锁（worker 不持有 `m_ringWorkerMutex`）。
7. **行为差异**：CPU 并行度从“多 worker 并发”降为“单 worker 串行 + 合并最新帧”，单帧吞吐不变，但持续过载时的总处理帧率下降（这是限流的目的）。
