# PAimage 与当前项目接收实现对比

日期：2026-09-09。结论针对用户提供的 PAimage_Setup.exe、当前最新分支固定快照，以及9月8日实机日志。

**结论：成功从安装包中提取并检查了 PAimage 原生程序，确认了接收实现和统计口径上的具体差异，但仍未获得能把两项丢包问题归因到某一处程序实现的证据。此次比较不能证明改成 PAimage 的接收方式就会消除丢包，也不能证明外接网卡就是根因。**

本报告接受用户已验证的触发正确性和采集卡发送完整性，将剩余定位范围限定为接收侧。可靠实验使用台式机+PCIe万兆网卡，当前实验使用笔记本+外接网卡，两次程序也不同；软件和硬件两个变量同时改变，不能通过结果差异单独归因。

## 2. 已确认的实现差异

| 比较项 | PAimage 1.5.16.0 | 当前项目最新分支 | 对根因判断的意义 |
|---|---|---|---|
| 数据接收方式 | 共享接收循环遍历socket列表，`select`后非阻塞`recvfrom`，逐socket读到would-block | 每4卡一个接收线程，`select`后逐socket读到would-block；现场4卡同组 | 基本模型相同，不能把共享接收循环本身认定为当前独有缺陷 |
| select超时 | 1,000µs | 1,000µs | 没有发现可用于解释差异的超时参数差别 |

## 3. 最重要的新发现：缺包显示口径不同

PAimage不是只有一个“丢包”数字。界面构造函数实际引用这些文字：

- “启动过滤（不计入采集丢帧）”
- “启动过滤卡触发”
- “启动缺包/未同步”
- “采集中缺包/未同步”

这不只是未使用的文本资源。反汇编确认：不完整卡触发进入同一个处理函数后，根据一个启动状态标志，分别对对象偏移`0x780`或`0x750`的计数器加1。通过统计快照拷贝和界面输出调用可追踪到，前者显示为启动缺包，后者显示为采集中缺包。

以下仅为反汇编重建的说明性伪代码；变量名由审核者命名，不是恢复出的原始源码：

```cpp
// VA 0x140135798—0x1401357b6：不完整卡触发分支
if (confirmed_state_flag) {
    runtime_incomplete_card_triggers += 1; // object + 0x750
} else {
    startup_incomplete_card_triggers += 1; // object + 0x780
}
```

证据链：[不完整触发处理函数](D:/ChatGPT/PAERealtimeImaging/CODEX_REPORTS/reliable-binary-analysis-20260909/fn-0x140134da0.asm) → [统计快照入口](D:/ChatGPT/PAERealtimeImaging/CODEX_REPORTS/reliable-binary-analysis-20260909/fn-0x1401436d0.asm) → [快照字段拷贝](D:/ChatGPT/PAERealtimeImaging/CODEX_REPORTS/reliable-binary-analysis-20260909/fn-0x14012d4b0.asm) → [界面文本及数值输出](D:/ChatGPT/PAERealtimeImaging/CODEX_REPORTS/reliable-binary-analysis-20260909/fn-0x1400c4500.asm)。对象`0x630`为快照基址，界面快照位于`rbp+0x30`；由此，`0x750`映射到`rbp+0x150`，`0x780`映射到`rbp+0x180`，分别由对应文本后的数值输出读取。

另外，`0x140132980`函数清理启动待处理数据及组包状态，并累计两个启动过滤计数（对象`0x778`与`0x770`）。接收路径存在等待间隔触发这一清理的调用；缓冲上限分支也会调用它。[启动缓存清理反汇编](D:/ChatGPT/PAERealtimeImaging/CODEX_REPORTS/reliable-binary-analysis-20260909/fn-0x140132980.asm)。是否在用户当时的具体配置和实测中触发，缺少PAimage现场记录，不能确定。

因此，“PAimage界面正式采集丢帧为0”与“当前项目首次触发报告缺3包”可以同时成立，不能仅由界面数字认定前者保住了首个物理触发。这不否定用户在台式机上验证的数据完整性；本次发现只限定两个程序的显示和计数不能直接比较。

PAimage上述不完整计数加1的单位是卡触发；当前项目部分触发缺22包时，packetsDropped会加22。即使处理同一组缺口，显示数值也可相差很多。将当前项目改为启动过滤或换计数单位，只会改变数据接纳/显示规则，不能补回已经缺失的原始包，不能用作本任务的修复验收。

## 4. 对两个问题分别能得出什么

### 问题一：每轮首触发

本次比较揭示了PAimage的启动过滤与计数分离机制，不能证明它在当前笔记本环境下能完整接收每轮第一个物理触发。

当前项目日志中，第一个已观察触发的四卡入口均有3包序号缺口，发生在组包之前；sessionBoundaryPacketsDiscarded、staleTriggerPacketsDiscarded及assemblyOffsetOutOfRangePackets均为0。此事实仍然成立。复制PAimage的启动过滤逻辑不能解释或修复这3包为何未出现在当前接收入口。

**最终原因：仍无法确定。此次没有发现可与该首触发缺口对应的、已被证明会丢掉这3包的当前程序分支。**

### 问题二：50µs持续采集

当前项目20µs与50µs阶段，部分触发次数从每卡12增加到681—684，入口断档事件从每卡10增加到327—336。这些是在同一当前程序中的比较，PAimage的不同统计口径不能把这部分异常解释掉。

64MiB与32MiB、优先级、CPU亲和性是已确认的可控差异，但没有socket溢出或故障时调度证据，不能认定其中任何一项造成此次丢包。尤其不能把“PAimage申请更大缓冲”直接写成“当前缓冲不足”。两者基本接收模型一致，也不支持先把共享接收循环替换掉就能解决问题的判断。

现有网络日志还显示：20µs阶段，采集网卡的单播接收增量与四卡socket接收增量相等；50µs阶段仅差4。它没有呈现与大规模缺口相当的“已被接口计数收到、却未被程序读取”的累计差额。这是限制简单socket积压归因的证据，但聚合计数不是逐包对照，不能证明具体硬件或驱动无故障。

**最终原因：仍无法确定。PCIE网卡与笔记本外接网卡的差异也仍是未分离的实验变量，不能通过静态反汇编消除。**

现场计数及时间证据均见[上一份实机丢包定位报告](D:/ChatGPT/PAERealtimeImaging/CODEX_REPORTS/field-log-analysis-20260909/实机丢包定位报告.md)。其中要求发送侧对照的后续建议，按用户新增约束调整为只在接收侧验证；本次没有再次要求修改或监控发送设备。

## 5. 是否因此改变重构建议

**不改变“暂不以重构作为已知修复方案”的建议。** 相比此前，现在有了两个明确可测的软件差异，可以在接收侧作小范围、可回退验证，无需先重构组包、成像或接收模型：

1. 在同一笔记本、同一外接网卡、同一采集条件下比较两份程序，并检查首触发、入口包序列及原始数据缺口；不能只比较界面丢帧数字。两程序应分时运行，避免占用相同端口。此验证不要求更改发送端。
2. 如果硬件实验只能运行当前程序，先补齐接收入口证据，再分别验证线程亲和性、请求优先级、接收缓冲大小这三个参数。每次只改变一项，避免即使改善也无法知道是哪一项起作用。
3. 一旦某个参数变化在相同条件下稳定消除首触发和持续缺口，再决定保留局部调整，或为已证实的接收瓶颈作小范围重构。若仅消除其中一个问题，不能宣称两者同源或全部修复。

这是一份验证优先级建议，不是对其中某项根因的概率背书。本轮未修改产品、未替换接收线程模型、未改变计数或过滤规则。
