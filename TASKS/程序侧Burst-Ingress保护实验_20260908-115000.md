# Host-side burst / ingress protection experiment

## 1. Objective

在不改变 FPGA、UDP wire format、socket 接收算法、DataProcessor、PacketAssemblyBuffer、Ring 协议、CUDA 重建算法和 UI 的前提下，进行一次**严格可回滚、单变量优先**的程序侧实验：

> 限制 `ImagingSvc` 对主机 CPU 调度资源的侵占，为 Windows NIC / USB / driver / DPC / lower-NDIS ingress servicing 保留稳定的 CPU 余量，验证当前四卡同步 burst 丢包是否可通过 host-side scheduling isolation 显著缓解。

本任务不是泛化“网络性能优化”，也不是继续修改已经证明守恒的应用 UDP 接收/组包路径。

核心实验变量只有：

1. `ImagingSvc` 进程 priority class；
2. `ImagingSvc` 进程 CPU affinity。

现有网络入口层观测必须完整保留，用于下一次实机 A/B 判定。

## 3. Evidence / Experimental Hypothesis

### 3.1 最新 20 us 实机结果

固定 4 卡、100 Hz、`acqTime=20000 ns`、每卡 28 packet/trigger：

```text
仅采集：
2001 trigger × 28 packet = 56028 packet/card
四卡 socketPacketsReceived 均完整到达
真实丢包约 0%

开启实时成像：
真实丢包约 8.8%/card
四卡高度同步
```

同一硬件、同一 burst、同一 2.5 Gb/s 链路，仅主机成像状态变化即可把丢包从约 0% 提升到约 8.8%。

### 3.2 50 us -> 20 us 的 scaling

此前 50 us、70 packet/trigger、实时成像时真实丢失约 27.4%；降到 20 us、28 packet/trigger 后约 8.8%。典型四卡同步 partial missing 也从约 22 packet/card 缩小到约 7~8 packet/card。

这支持：

```text
synchronized burst size
+
host ingress servicing / buffering capacity
```

共同决定丢包严重度。

### 3.3 当前 ingress 分层证据

最新实机继续满足：

```text
Windows interface ΔInUcastPkts
== Σ ΔsocketPacketsReceived

socketPacketsReceived
== processorPacketsDequeued

interface InDiscards = 0
interface InErrors   = 0
UDP InErrors         = 0
recvHardErrors       = 0
selectErrors         = 0
```

因此大量真实缺失发生在 Windows interface successful-RX accounting 之前；本任务不应继续优化 `recvfrom()` 之后的队列/组包路径。

### 3.4 当前具体假设

本次只验证下述因果假设：

```text
四卡同步 burst
    +
ImagingSvc 主机负载
    -> NIC / USB / driver / DPC / lower-NDIS ingress servicing 余量下降
    -> InUcastPkts 之前的有限 buffer / descriptor / transport path overflow
    -> 成批 UDP packet 缺失
```

若限制 ImagingSvc CPU 调度资源后丢失显著下降，则该假设得到强支持；若无明显变化，则停止继续做应用层泛化优化，转入 ETW/NDIS/USB/DPC 观测与采集时间梯度实验。

## 4. Current Scheduling Facts

当前 4 卡接收路径：

```text
NetworkController:
CARDS_PER_RECEIVER = 4
first receiver cpuCore = 2
```

`MultiPortReceiver::run()` 当前已经：

```text

SetThreadPriority(GetCurrentThread(), THREAD_PRIORITY_TIME_CRITICAL)
```

本任务**不得修改以上 receiver affinity / priority 行为**。

`ImagingSvc` 是独立 `QProcess` 子进程，当前 `src/ImagingSvc/main.cpp` 未设置 process priority class 或 process affinity。这是本实验唯一允许主动修改的主路径。

## 5. Required Intervention

### 5.1 Windows ImagingSvc process priority

在 `ImagingSvc` 启动早期、进入重建事件循环之前，对当前 ImagingSvc process 调用 Windows process-level scheduling API。

目标 priority class：

```text
BELOW_NORMAL_PRIORITY_CLASS
```

推荐：

```cpp
SetPriorityClass(GetCurrentProcess(), BELOW_NORMAL_PRIORITY_CLASS)
```

不得使用：

```text
IDLE_PRIORITY_CLASS
REALTIME_PRIORITY_CLASS
HIGH_PRIORITY_CLASS
```

也不得调整 receiver thread priority 作为本实验变量。

调用失败不得导致 ImagingSvc 启动失败；必须记录 Win32 error，并继续以原 priority 运行。

### 5.2 Windows ImagingSvc process affinity

本次实机固定 4 卡，现有 receiver group 固定占用 logical CPU 2。

实验目标：让 ImagingSvc 不在以下 logical processors 上执行：

```text
CPU 2 : 当前 4-card MultiPortReceiver 专用核
CPU 0 : 额外保留给 OS / interrupt / DPC / driver servicing 的实验性余量
```

因此，在安全可行时：

```text
ImagingSvc allowed mask
= current process affinity mask
  - CPU0
  - CPU2
```

实现不得假定所有机器一定具有 CPU2。必须：

1. 使用 `GetProcessAffinityMask()` 读取 process/system mask；
2. 仅清除当前有效 mask 中实际存在的 CPU0/CPU2 bit；
3. 若清除后 mask 为 0，禁止调用 `SetProcessAffinityMask(0)`；退化为较保守的 mask 或完全不改 affinity；
4. 若机器逻辑处理器过少，必须优先保证 ImagingSvc 可运行；
5. affinity 调用失败只记录 error，不得导致 ImagingSvc 退出；
6. 调用后重新 `GetProcessAffinityMask()`，记录 effective mask，不能只记录 requested mask。

最低安全规则建议：

```text
active usable logical processors >= 4:
    try exclude CPU0 + CPU2

otherwise:
    do not force two-core exclusion;
    keep original affinity and only apply BELOW_NORMAL priority
```

允许等价、更保守的 fallback，但不得扩大到修改 NIC RSS/interrupt affinity。

### 5.3 Scope of affinity

必须使用**process affinity**约束 ImagingSvc，而不是只 pin Qt main thread；这样 ImagingSvc 内部由 reconstruction / CUDA runtime 创建的普通 CPU worker threads 也继承该 process scheduling boundary（除非第三方显式覆盖）。

本任务不得修改 CUDA kernel、GPU stream、reconstruction 数学或 Ring block 行为。

## 6. Implementation Shape



```text

```

或等价的“进入实际 reconstruction 工作之前”位置。

不得修改 `ImagingController` 的业务协议来实现该功能；若无需父进程配合，优先保持 `ImagingController.cpp` 不变。

## 11. Real-hardware Experimental Protocol After Code Approval

Codex 不执行真实 FPGA/NIC 实机结论；实机由用户完成。

正式审核通过后，下一轮优先保持与最新干净 A/B 相同条件：

```text

100 Hz
acqTime = 20000 ns

```

建议至少两个连续区间：

```text

B. realtime imaging ON, save OFF, >=2001 triggers
```

主要比较：

```text

processorPacketsDequeued
sameTriggerForwardGapPackets/events
stale/duplicate/offset rejection counters
receiver maxDrainPackets
maxDrainDurationUs
maxReceiverLoopGapUs

```

判定原则：

```text

    强支持 host ingress servicing starvation / resource contention 假设；
    再决定是否把 scheduling isolation 产品化。

若有中度改善但仍明显丢包：
    host servicing 是因素之一；
    下一步增加 ETW/NDIS/USB/DPC 观测并做 10/20/30/40/50 us 梯度。

若基本不变：
    停止继续做应用层 scheduling 优化；
    转向低层 ingress observability + 梯度实验。
```

注意：第一段/跨采集段 triggerSeq 大跳造成的整-trigger inferred `packetsDropped` 必须继续与真实 partial missing 分开分析，不能直接拿累计 `packetsDropped` 当真实网络 loss。
