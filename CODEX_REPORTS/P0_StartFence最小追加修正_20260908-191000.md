# P0 Start-Fence 最小追加修正执行回执

## 1. 核实结论

网页端反馈的问题属实。MIN_FIX_BASE_SHA 的 MeasurementSessionTransaction 先执行全局 receiver commitSession()，再一次性调用全局 doSendStartMeasure()；MultiPortReceiver 也只有一个全局 admission 状态。因此存在以下软件竞态：

~~~
全局 receiver Commit -> 所有卡已 RUNNING
                      -> 逐卡硬件 Start 尚未发送
                      -> 旧 session trailing packet 被新 session 接收
~~~

上一轮修正关闭了 Start 后 receiver 尚未打开的一侧窗口，但留下了上述相反窗口。本次只修正 Start-fence，上一轮通过的诊断日志时间窗导出和其它 P0 内容保持冻结。

## 3. 实际 Start-fence 设计

MultiPortReceiver 现在为每个 socket/card 保存独立的 admission state 和 session token：

~~~
Prepare：所有卡 DISARMED -> PREPARING，并排空旧 socket backlog
Arm：所有卡进入 ARMED，仍拒绝 datagram
每张卡：local hardware Start sendto 成功 -> commitCardSession(cardIndex)
       -> 该卡立即 RUNNING，可 dispatch 新 packet
4/4 card fence 成功 -> controller RUNNING / measurement_started
~~~

MeasurementSessionTransaction 不再接受全局 Commit-before-Start 回调，而是按 cardIndex 顺序调用单卡 Start sender；单卡本地发送成功后立即调用该卡 fence。发送失败或 fence 发布失败都会触发现有 rollback/teardown。receiver 的生产 run() 和测试 seam 继续共用：

~~~
parse -> per-card admission(token/state) -> raw observe -> processor enqueue
~~~

因此不存在全局提前开门，也不存在等待四卡发送完成才统一开门。每张卡在自己的 local sendto 成功前继续计入 sessionBoundaryPacketsDiscarded；成功后不等待其它卡即可接收。Start-fence 事件包含 measurementSessionId、cardIndex、targetIP、startFenceCommitted。

## 4. 必要回归证据

### T2 exact Start-fence window

session_boundary_receiver_test 通过 dispatchDatagramForTest() 调用生产 dispatchDatagram()，未直接调用 DataProcessor::enqueuePacket()。测试时序为：

~~~

模拟该卡 local Start 尚未发布 fence，再 inject old trailing #2 -> boundary discard
模拟 local Start send 成功，调用 commitCardSession(card 0)
立即 inject session B first packet #0，再注入该 trigger 剩余 packet
~~~

断言全部通过：

~~~

packetsDropped delta = 0
triggersPartial delta = 0
staleTriggerPacketsDiscarded delta = 0
pre-fence packet 只增加 sessionBoundaryPacketsDiscarded
raw anchor 属于 fence 后正式首包
~~~

### T3 4-card sequential fence

同一测试使用一个生产 MultiPortReceiver 的四个 socket/card 和四个 DataProcessor：

~~~
card0 fence 前 packet -> discard；card0 send/fence -> packet 立即入队
card1 尚未 fence 时仍 closed；随后 card1 send/fence -> packet 立即入队
card2、card3 按同样顺序执行
~~~

测试确认四张卡全部 fence 前 aggregate state 不为 RUNNING，仅在 card3 fence 后变为 RUNNING，并且每张卡 fence 后的 packet 均被接收。

## 6. Frozen files / boundary limitation

以下上一轮已通过文件相对 MIN_FIX_BASE_SHA 均为 0 diff：

~~~

~~~

本修正关闭的是软件可定义的 Start boundary race。若旧 UDP datagram 在物理网络或驱动层直到 fence 之后才首次到达 host，在没有 wire-level session epoch/硬件 ACK 的前提下，软件无法仅凭 payload 绝对区分旧 session 与新 session；本任务没有修改 FPGA 协议，也没有伪造绝对可区分的结论。

软件测试、loopback 和 Ring selftest 不等价于四卡实机零丢包证明；正式四卡实机测试仍需 ChatGPT 复核通过后执行。
