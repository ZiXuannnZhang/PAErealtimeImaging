## 4. 阻塞缺陷 A：旧 session trailing packet 可获得新 token

当前实现的关键顺序是：

```text
DataProcessor::prepareSession()
  -> drain input queue / reset assembly / gate off
DataProcessor::armSession()
  -> drain input queue
  -> m_ingressSessionToken = new token
  -> m_activeSessionToken = new token
  -> gate on
NetworkController
  -> doSendStartMeasure()
```

`MultiPortReceiver` 收包时先执行 raw-order observe，再调用：

```text
DataProcessor::enqueuePacket(pkt)
```

而 `enqueuePacket()` 是按**包进入 DataProcessor 的时刻**读取当前 ingress token 打标。

因此下面的生产时序仍可能污染新 session：

```text
上一 session hardware Stop 已发送
旧 UDP packet 仍在 NIC / Windows UDP socket / receiver 路径中
新 session processor 已 ARMED
旧 packet 此时才被 receiver 取出
-> 被错误打上 new token
-> 可进入新 assembly / 新 raw anchor
```

### 4.1 必须实现 receiver-aware session boundary

具体类设计由 Codex 决定，但必须满足以下行为：

1. measurement session admission 不能只在 DataProcessor `enqueuePacket()` 时靠当前 token 推断；
2. `MultiPortReceiver` 或等价真实 ingress owner 必须参与 session prepare/arm boundary；
3. PREPARING 期间生产 ingress admission 必须关闭；
4. receiver 必须在自己的线程/ownership 下完成旧 socket backlog 的 drain/quiescence barrier，不能由 GUI/controller 并发操作 socket；
5. barrier 必须是**基于 receiver 实际无待处理数据的条件**，不得通过固定 sleep 或“先丢 N 个 trigger”实现；
6. barrier 必须 bounded timeout；任一 receiver prepare/quiescence 失败时，禁止发送任何 hardware Start；
7. processor reset 与 receiver ingress reset 完成后才能进入 ARMED；
8. Start transaction commit 前不能让 PREPARING/ARMED 期间到达的旧 packet 成为新 session assembly 或 raw-order anchor；
9. hardware Start command 仍必须在所有 receiver/processor barrier 成功以后发送；
10. 不允许重新引入“hardware 已发送，但 processor 尚未 armed”的旧竞态。

允许使用明确的 session admission epoch/state，例如：

```text
DISARMED
PREPARING
ARMED
COMMITTING/RUNNING
```

也允许其他等价实现。

如果需要把 receiver 的 datagram parse/dispatch 抽成一个生产和测试共用的小函数，可以做；测试 hook 必须调用**与生产 run() 相同的 dispatch/admission 逻辑**，不得建立一套只为测试存在的伪路径。

### 4.2 raw-order anchor 语义

必须满足：

- `socketPacketsReceived` 等 cumulative counters 继续保持 cumulative；
- session boundary 不得清零累计 raw-order / assembly counters；
- 但 raw receive **anchor** 必须是 session-scoped；
- DISARMED / PREPARING / 未提交到当前 session 的 trailing packet 不得重新建立当前 session raw anchor；
- 新 session 第一条被正式 admission 的 packet 才能建立新 raw anchor；
- 不得改变 `observeRawReceive()` 已审核的正常包 gap/backstep/duplicate 判断算法，除非只做必要的调用门控或 anchor reset 封装。

## 5. 阻塞缺陷 B：disarm/reset barrier 失败被忽略

当前 `resetProcessorsAfterSession()` 对：

```text
processor->disarmSession(1500)
```

的返回值未聚合、未传播。

正常 Stop 还会在确认 processor disarm/reset 之前记录 `measurement_stopped`。

### 5.1 必须改为有结果的 teardown transaction

Stop / rollback 必须满足：

1. 正常 RUNNING：先 attempt hardware Stop；
2. 然后执行所有 receiver + processor 的 disarm/reset bounded barrier；
3. 每个 barrier 的 success/fail 必须聚合并记录；
4. 只有 hardware Stop 的本地发送语义和本地 teardown 状态达到任务定义的成功条件后，才能记录 canonical `measurement_stopped`；
5. 任一 receiver/processor disarm/reset timeout/failure 时，不得记录成功 `measurement_stopped`；必须记录明确 `measurement_stop_failed` 或等价 canonical failure，reason 至少能区分：
   - hardware stop send failed；
   - receiver disarm failed；
   - processor disarm failed；
6. start partial-send rollback 同样必须检查 teardown 结果，不能 best-effort 调用后无条件把本地状态当作干净；
7. 如果本地 session cleanup 未完成，必须进入明确的 fault/uncertain 状态，后续 Start 不得静默创建新 session；
8. 可以提供 bounded retry/恢复路径，但不得无限阻塞 GUI，也不得在 packet hot path 做同步等待；
9. failure 状态必须可通过日志和 controller state 明确判断。

禁止用“忽略 disarm 失败但下一轮 prepare 再清一次”作为修复。

## 6. 阻塞缺陷 C：pending measurement session 状态泄漏

当前存在至少两条风险路径：

```text
sendStartMeasure()
-> newMeasurementSessionId()
-> m_pendingMeasurementSessionId = id
-> ConfigPhase::Failed
-> return false
```

以及 queued Start 后配置失败、命令从队列移除的路径。

### 6.1 必须满足

所有 Start request 终止路径必须有确定的 session-ID ownership：

- immediate reject；
- config failed；
- ready/config queued 后最终 reject；
- processor/receiver prepare failure；
- arm failure；
- hardware start send failure；
- partial start rollback；
- successful start；
- stop / stop failure。

不得留下 orphan `m_pendingMeasurementSessionId`。

在一个失败请求完成 cleanup 后，如果系统没有进入 boundary-fault 状态，则用户重新配置并发起 Start 必须能够生成新的 session ID 并正常进入 transaction。

不得通过随意 `clear()` 掩盖正在运行/状态不确定的真实 session。

## 7. Boundary diagnostics 补齐，但不修改时间窗导出实现

使用现有 `DiagnosticRecorder` API 补齐 session boundary 记录。

### 7.1 Start / Stop / rollback 对称快照

以下边界至少主动记录：

```text
measurement_session_prepare
measurement_started
measurement_start_rollback / measurement_start_failed
measurement_stop_command
measurement_stopped / measurement_stop_failed
```

每个关键边界应尽可能包含：

- current settings/config snapshot；
- 四卡 cumulative runtime counter snapshot；
- runtime_ingress / interface snapshot；
- `measurementSessionId`；
- `configId`；
- command successCount/failCount；
- receiver prepare/disarm success/fail counts；
- processor prepare/arm/disarm success/fail counts；
- outcome/reason。

尤其 stop/rollback/failure 不能只写 event + ingress/card，而缺少与 start 对称的 settings/config snapshot。

### 7.2 canonical lifecycle event 去重

一个实际 session 的 canonical lifecycle marker 每个语义只允许出现一次。

例如：

```text
measurement_session_prepare
measurement_session_armed
measurement_start_command
measurement_started
measurement_start_failed
measurement_start_rollback
measurement_stop_command
measurement_stopped
measurement_stop_failed
```

不得 helper observer 和 NetworkController 各写一遍同名 canonical event。

若需要保留 helper 内部步骤，可使用明确不同的 category/message，例如 internal transaction step；不得与 canonical marker 重名导致时间窗分析误判 session 边界。
