## 3. 实现结果

MultiPortReceiver 增加 receiver-owned per-card admission states：

    Disarmed -> Preparing -> Armed -> StartFenceHold -> Running

增加 API：

    beginCardStartFence(sessionToken, cardIndex, timeoutMs)
    completeCardStartFence(sessionToken, cardIndex, startSucceeded, timeoutMs)

生产 Start 顺序现在是：

    begin fence
    -> receiver thread 校验 card/token/ARMED，先发布 HOLD
    -> receiver thread 对该卡做最终 closed-admission quiescence
    -> 本地 send Start(card)
    -> send 成功时 complete(..., SUCCESS)，先发布 RUNNING，再恢复正常 drain
    -> send 失败时 complete(..., FAILURE)，关闭 admission 并清理 backlog，再走 rollback/teardown

MeasurementSessionTransaction callback contract 已改为显式表达：

    beginFence(card) -> sendStart(card) -> completeFence(card, success/failure)

事务结果增加 begin/complete 成功与失败计数，并保留 begin/send/complete/failure-cleanup/rollback 阶段标记。begin 失败、send 失败、complete 失败和 partial start 均进入现有 rollback 生命周期。

## 4. HOLD、quiescence 与 receiver 主循环

begin command 在 receiver thread 内先把目标 card 置为 StartFenceHold，然后调用显式的 StartFenceQuiescence drain 到 WSAEWOULDBLOCK。quiescence 中读到的内容只走 closed-admission boundary discard，不进入 observeRawReceive 或 processor。

正常 run 路径在构建 fd_set 时跳过 HOLD card；因此 HOLD 期间即使 UDP kernel backlog 可读，也不会执行该卡的正常 recvfrom / drainSocket / dispatch。若当前 receiver group 没有 eligible socket，使用 bounded command wait，不调用 empty Winsock select。原有 1 ms select timeout 未修改。

HOLD 期间新 session 数据留在 kernel backlog。SUCCESS complete 在同一 receiver command 处理内先发布 RUNNING，之后才允许普通 readable/drain，因而 backlog 中的同一批数据由生产 receive/dispatch 路径消费。FAILURE complete 不发布 RUNNING，关闭 card admission，并对 HOLD backlog 做 closed-admission 清理。

aggregate admission state 在任一 card 为 HOLD 时导出 StartFenceHold；单卡 state 可独立推进，已 RUNNING card 不会被其它卡的 HOLD 打开。Network snapshot 将该状态序列化为 start_fence_hold，不会误报为 running 或 disarmed。
