## 1. Objective

围绕当前 `main` 上“每轮采集启动段触发跳号 + 不完整触发/丢包”的现场问题，完成两个彼此独立但必须闭环的验证工作：

1. **构造确定性的真实 UDP START-race 集成测试**，覆盖当前自动化测试没有覆盖的真实硬件时序：某张模拟采集卡在收到自己的 START 后立即发送首触发，而此时主机仍可能在向其他采集卡逐卡发送 START。验证当前 PAimage-derived production path 在该时序下是否会出现：
   - raw ingress 已经成功进入应用；
   - SourceCore 因 START admission 尚未打开而判定 `Disabled`；
   - 由此产生首触发完全消失（trigger jump）或首触发部分数据丢失（partial/incomplete）的可重复现象。

2. **增强 `startup_diagnostics_analyze.py`**，把仓库当前已经记录但尚未自动关联的证据串起来：

```text
stage 6: per-card START send
        -> stage 1: raw recvfrom ingress
        -> stage 2: SourceCore decision
```

输出逐 measurement session、逐卡、逐 ingress correlation 的 START admission 证据，使真实现场 ZIP 不再需要人工翻二进制 trace 才能判断“应用是否在 START gate 内主动丢弃已经收到的包”。

本任务的目标是**验证机制和完善证据链**。无论测试是否复现，都不得在本任务内直接修改 SourceCore admission、START 控制顺序、SocketReceiver 调度策略或生产组包策略来“顺手修复”。

## 3. Problem / Evidence

### 3.1 当前真正的生产采集路径

不要按旧 `MultiPortReceiver -> DataProcessor -> PacketAssemblyBuffer` 路线实施本任务。

当前 `NetworkController::start()` 无条件进入 PAimage-derived backend，production path 为：

```text
FPGA / acquisition cards
  -> Windows UDP sockets
  -> PaimageAcquisition::SocketReceiver
  -> PaimageAcquisition::SourceCore
  -> PaimageAcquisition::HostOutput
       -> CardFrame save path
       -> SyncFrame -> DataProcessor::deliverAssembled
                      -> Display / Ring / Publisher
```

### 3.2 已审查到的 START transaction

当前 `Backend::startMeasurement()` 语义：

```text
prepare lambda:
    session_ = session
    receiver_.prepareStart(session)
    output_.beginSession(session)

sender_:
    ControlSocket::send(START, allCards)

complete lambda:
    receiver_.completeStart(ok)
```

`ControlSocket::send()` 对 `cards` 顺序逐个执行 `sendto()`，不是原子广播。

`SourceCore::prepareStart()`：

```text
enabled_ = false
清 pending / active assembly / recent 等会话状态
```

`SourceCore::ingest()`：

```text
if (!enabled_) -> Decision::Disabled
```

`SourceCore::completeStart(true)` 才：

```text
enabled_ = true
```

因此源码上存在如下候选竞争窗口：

```text
prepareStart()  [admission closed]
    |
    +-- START -> card 0
    |      card 0 may immediately send UDP
    |      SocketReceiver may recvfrom successfully
    |      SourceCore may return Disabled
    |
    +-- START -> card 1
    +-- START -> card 2
    +-- START -> card 3
    |
completeStart(true) [admission opened]
```

本任务必须验证这个窗口，不得仅通过代码阅读宣布其为现场根因。

### 3.3 当前自动化测试盲区

现有测试的关键问题：

- `tests/paimage_core/socket_replay.cpp` 在发送采样数据之前先执行 `prepareStart()` + `completeStart(true)`；
- `tests/paimage_core/protocol_checks.cpp` 也是 START 事务返回后再注入采样数据；
- `tests/paimage_network_test.cpp` 的模拟采集卡会先等 host 完成 START 命令读取，再进入采样发送循环。

因此它们没有覆盖“某卡收到自己的 START 立即回数据，而其他卡 START 尚未完成”的真实场景。

### 3.4 当前 trace 已经具备的证据

`SocketReceiver` 当前 trace：

- **stage 1**：成功 `recvfrom` / `WSARecvMsg` 后立即写 raw ingress；发生在 feedback demux / admission / dedup / SourceCore 之前。
- **stage 2**：SourceCore observation/decision。
- stage 1 raw ingress 的 `correlation` 是 ingress ID。
- stage 2 对当前包的事件若没有 frame firstIngressId，会使用当前 receiver correlation，因此可与 stage 1 ingress ID 精确关联。

`Backend` 控制发送 observer 当前写：

- **stage 6**；
- `reason = command[4]`；
- START command 的 `reason == 3`；
- `card` 为目标卡；
- `sourceIPv4` 为目标卡地址；
- `length` 为 `sendto()` 返回字节数；
- `value` 为发送错误码；
- `session` 已在 START prepare lambda 中设置为新 measurement session。

因此 trace 本身已经足够完成 START send -> raw ingress -> Source decision 的应用内闭环。

### 3.5 当前分析器缺口

`tools/startup_diagnostics_analyze.py` 当前主要解析：

- stage 1 raw ingress；
- stage 2 rejects / source observations；
- LoopLog；
- Pktmon/WPR/system manifest；
- round storage；
- clock anchors。

但当前没有把 **stage 6 START send** 纳入统一 startup causal timeline，也没有把 stage 1 / stage 2 按 correlation ID 自动联结为“raw packet entered app but was Disabled by START admission”。

## 6. Recommended Design

### 6.1 Part A — 确定性 START-race UDP 集成测试

优先新增一个独立测试，例如：

```text
MC_410T_MultiCard/delivery/tests/paimage_start_race_test.cpp
```

文件名可以调整，但测试必须独立可运行、可在 CTest 中单独定位。

#### 测试必须使用真实 WinSock UDP

不得只直接调用 `SourceCore::ingest()` 来宣称覆盖 START race。

至少需要：

- 当前 `ControlState` / `ControlSocket` 的真实 UDP control send；
- 当前 `SocketReceiver` 的真实 UDP socket + receive thread；
- 当前 `SourceCore` admission；
- 4 个逻辑卡目标；
- 每卡在收到自己的 START 后立即产生采样 UDP。

可以直接使用 `Backend` / `NetworkController`，也可以组合当前 production components；但最终证据必须覆盖实际逐卡 START send 与并发 receiver thread。

#### 推荐 loopback 布局

可参考现有 `paimage_network_test.cpp`：

```text
host local: 127.0.0.1
card0: 127.0.0.2:8080 -> data 127.0.0.1:8001
card1: 127.0.0.3:8080 -> data 127.0.0.1:8002
card2: 127.0.0.4:8080 -> data 127.0.0.1:8003
card3: 127.0.0.5:8080 -> data 127.0.0.1:8004
feedback: 127.0.0.1:8000
```

不要依赖广播、多播或真实 NIC。

#### 必须确定性，不接受“多跑几次偶尔撞到”

纯粹依赖 `Sleep(1)`、线程调度和 loopback 时序可能导致 flaky test，不可接受。

允许采用以下之一：

- test-only callback / barrier，在 `ControlSocket::send()` 每卡 `sendto()` 返回后、进入下一卡前建立测试同步点；
- test-only sender seam，确保仍然使用同样的逐卡 send 语义，并能在卡 0/1 START 已发送、卡 2/3 尚未发送期间等待模拟卡完成首包发送；
- 等价的 condition variable / event / latch 设计。

要求：

- production compile 不包含任何等待；
- production runtime behavior 不变；
- 不能只在测试里手工调用 `prepareStart()` / `completeStart()` 之间注入包而绕过真实逐卡 START 发送，因为这无法验证 control-send ordering 与 receiver concurrency 的组合。

#### 场景 A：整首触发落在 gate 内 -> trigger jump

至少一个 early card 做：

1. 收到自己的 START；
2. 在 host `completeStart(true)` 前发送一个**完整首触发** T0（所有 packetSeq）；
3. 等 START transaction 完成；
4. 再发送完整 T1。

必须验证：

- T0 所有发送包确实被 host stage 1 raw ingress 观察到；
- 对应 ingress correlation 的 stage 2 decision 为 `Disabled`；
- T0 不产生 accepted complete output；
- T1 正常 complete；
- 从有效输出视角首个 trigger 可成为 T1，即形成可解释的 trigger jump；
- 不能把该结果称为“socket 丢包”，因为 stage 1 已证明 raw ingress 存在。

建议使用非 0 trigger（例如 100 / 101），避免测试输出被“trigger 0 特殊处理”误导。

#### 场景 B：首触发前缀在 gate 内、后缀在 gate 后 -> partial

至少一个 early card 做：

1. 收到 START；
2. 在 admission 关闭时发送 T200 的前 K 个 packet（例如 packet 0..7）；
3. 等 completeStart 后发送 T200 剩余 packet；
4. 再发送 T201 以强制关闭/切换 T200，或等待 timeout。

必须验证：

- gate 内前缀 stage 1 存在且 stage 2 = `Disabled`；
- gate 后剩余包进入 SourceCore；
- T200 最终不能成为 complete frame；
- 能观察到 partial/TriggerSwitch/Timeout 对应证据；
- 缺包数与被 gate 丢弃的前缀数量是否一致必须记录；若因 first-arrival `basePacket` 语义导致数量/位置不同，测试报告必须解释，不得强行改源码使期望“好看”。

#### 场景 C：control / admission 完成后的正常对照

所有卡在 START complete 后发送正常完整 trigger，必须全部 complete，证明新测试基础设施本身没有破坏 production path。

#### 重复性

至少连续运行同一确定性测试 20 次或在单进程内做 >=20 measurement sessions。要求：

- 不依赖概率碰撞；
- 每轮场景 A/B 的预期 evidence 都稳定出现；
- 正常对照每轮稳定 complete；
- 无 socket hard error；
- 无 trace queue drop；
- 无 test deadlock；
- 每个等待都有明确 timeout，失败时打印当前 card/session/phase。

### 6.2 Part B — Analyzer START admission timeline

增强：

```text
MC_410T_MultiCard/delivery/tools/startup_diagnostics_analyze.py
```

建议新增顶层输出：

```json
"startAdmissionEvidence": {
  "status": "...",
  "sessions": [...],
  "summary": {...},
  "limitations": [...]
}
```

字段名可调整，但必须 machine-readable，不能只输出自然语言。

#### 必须解析 stage 6 START send

START 识别条件至少为：

```text
stage == 6
reason == 3
```

并保留：

- session；
- card；
- sourceIPv4；
- monotonicNs；
- send byte count / `length`；
- send error / `value`；
- trace sequence（如可用）。

同一 session 内按 monotonic/sequence 排序，给出：

- first START send；
- last START send；
- per-card START send；
- card send order；
- send span ns/us；
- send failure 状态。

#### stage 1 -> stage 2 必须优先按 correlation 精确 join

对每个 stage 1 raw ingress：

```text
(session, correlation [, card])
```

查找对应 stage 2 decision。

不得只用 `(trigger, packet)` 做 join，因为：

- 16-bit trigger 可跨轮复用；
- 同一 packet number 可重复；
- raw trace 已经提供 ingress correlation，应使用更强证据。

必须统计：

- raw ingress count；
- matched stage2 decision count；
- missing stage2 join count；
- Disabled count；
- Accepted count；
- Duplicate / OffsetOutside / RecentTrigger 等其它 decision count。

对于 stage2 correlation 缺失或 trace 不完整，不得默认为 Accepted。

#### 每卡 START 证据

每个 measurement session / card 至少输出：

- `startSendNs`
- `startSendSucceeded`
- `firstRawIngressAfterStartNs`
- `firstRawIngressAfterStartLatencyNs`
- first raw trigger / packet
- `disabledIngressCount`
- 第一个 Disabled ingress 的 trigger / packet / time / correlation
- 第一个 Accepted ingress 的 trigger / packet / time / correlation
- 在 first START send -> last START send 区间内的 raw ingress 数
- 其中 matched Disabled 的数量
- unmatched decision 数

如果存在 LoopLog control mark，允许附加 prepareStart / completeStart 边界，但 analyzer 的基本 START gate 判断不能强依赖 LoopLog 文件一定存在。

#### 分类规则

至少区分：

```text
application_start_gate_drop_observed
no_application_start_gate_drop_observed
control_send_failed
trace_incomplete
start_trace_missing
unverifiable
```

核心规则：

- **只有 stage 1 raw ingress 存在且同一 ingress correlation 的 stage 2 明确为 Disabled，才能声明 `application_start_gate_drop_observed`。**
- 这个分类只证明“应用已经从 socket 成功收到的数据被 START admission 拒绝”，不能证明这是现场全部物理丢包的唯一来源。
- stage 1 缺失不能推断卡未发送。
- system Pktmon 缺失也不能单独推断 FPGA/NIC 根因。
- trace summary 显示 `traceIncomplete` / queue drop / write failure 时，负面结论（“没看到 Disabled”）必须降级为 unknown/unverifiable。

#### 系统证据保持分层

现有 system capture evidence matrix 不得被弱化。

建议在 evidence matrix 增加一项：

```text
application_start_admission
```

但不要把它与：

```text
system_pktmon
wpr_scheduling
clock_alignment
```

混成单一“root cause”字段。

### 6.3 Part C — Analyzer synthetic regression

必须为 analyzer 新逻辑增加自动化测试/fixture。

至少覆盖：

1. **positive gate-drop fixture**
   - session 1；
   - 4 张卡 stage 6 START；
   - card 0 在 START span 中有 stage 1 ingress；
   - 相同 correlation 的 stage 2 = Disabled；
   - analyzer 必须分类 `application_start_gate_drop_observed`。

2. **accepted-only fixture**
   - stage 1 ingress 均有 matched Accepted；
   - trace 完整；
   - analyzer 不得误报 gate drop。

3. **incomplete trace fixture**
   - trace summary queueDropped > 0 或 traceIncomplete=true；
   - analyzer 不得因为没找到 Disabled 就输出强负面结论。

4. **correlation-over-number fixture**
   - 跨 session 重用相同 trigger/packet；
   - analyzer 必须按 session/correlation 关联，不得串轮。

5. **control send failure fixture**
   - stage 6 START `value != 0` 或发送长度异常；
   - 分类必须能区分 control-send failure 与 admission drop。

测试 fixture 应尽量小，不得提交大体积二进制 dump。

## 13. Acceptance Criteria

只有同时满足以下条件，Codex 才可把任务标为 implementation complete（但仍不能自行 APPROVE）：

### A. Deterministic race coverage

- 新测试覆盖真实 UDP control + receive concurrency；
- 不再是 `prepareStart(); completeStart(); 然后发数据` 的旧测试模式；
- scenario A 稳定证明或稳定反证“raw ingress + Disabled”；
- scenario B 稳定证明或稳定反证 partial 路径；
- scenario C 正常对照完整；
- 20+ 次重复无 flaky。

如果测试结果**没有**出现 Disabled，也可以完成任务，但必须证明测试确实把数据发送发生在 START transaction 尚未 complete 的窗口中；不能因为测试时序没打中而宣称机制不存在。

### B. Analyzer causal join

- stage 6 START 已解析；
- stage 1 -> stage 2 使用 session/correlation 精确关联；
- 输出逐 session / card evidence；
- trace incomplete 时结论降级；
- control send failure 与 admission drop 分开；
- 跨 round 重复 16-bit trigger 不串联。

### C. No production fix

- START / SourceCore / SocketReceiver production semantics 未改变；
- 如加 test seam，delivery build 不定义、不执行。

### D. Regression

- 新测试通过；
- analyzer tests 通过；
- core tests 实际执行并记录；
- delivery tests 实际执行并记录；
- 没有未解释的新 regression。

### E. Evidence quality

最终报告必须明确区分：

```text
Observed
Inferred
Not verified
```

禁止使用下列无证据结论：

- “已经证明 FPGA 丢包”；
- “已经证明 NIC 不丢包”；
- “START race 就是唯一根因”；
- “自动测试通过，因此实机没有问题”。
