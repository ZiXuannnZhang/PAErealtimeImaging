# PAimage移植版实机采集核实与定位报告

日期：2026-09-10。仅分析证据，未修改产品源码、原有分支、交付程序、网卡配置或原始数据。

## 结论

1. 三段连续采集的开头均有缺包及整段触发序号不可见，用户关于前期异常的观察成立。
2. “进入连续采集后直到周期完成不再丢包”不成立。三段分别有3、7、20个不完整触发（每卡相同的触发集合），包括中后段；最后一次缺包距离最后数据约4.24秒。
3. 三段报文触发序号跨度均为4001；实际收到的不同触发数分别为3918、3925、3912。没有本次物理触发边沿记录，不能将序号跨度等同实际物理触发次数。
4. 本次数据缺失在应用原始入口recvfrom返回记录中已经存在，不是已收到的数据被后续组包、启动过滤或保存队列漏掉。根因仍无法明确到接收硬件、驱动、内核或接收程序调度；不能据此宣布硬件损坏，也不能宣布程序完全无关。
5. 确认了另一项独立软件行为：源启动规则会主动过滤已接收的孤立启动数据，包括完整触发。本次过滤了触发1及2，但它不能解释三段连续采集的首包缺失和中后段缺包。

## 保存文件核实

12:53:04.951开始保存，12:54:11.598停止保存，覆盖第三段所有接收数据。每通道文件长度为12,500,000×3+11,400,000=48,900,000字节。保存格式每点float16、每触发6250点，因此每通道3912条，与日志和stage7保存成功回调3912条一致。

按源保存输出顺序关联：触发8006以及8096—12006写入；8007—8095未在入口出现，没有合成89条全零触发填洞。3912条中3892完整、20条不完整并补零；没有整条全零的保存记录。完整触发参与源同步成像，不完整触发仅走单卡保存路径，因此成像连续或视觉正常不能证明原始数据完整。

已逐个通道读取DAT内容，检查20条不完整触发对应的全部缺包样本区域：卡1每通道68,300个样本，卡2—4每通道69,200个样本，全部为零，与SourceCore补零实现一致。各文件SHA256和检查结果保存在`saved-data-verification.json`。这验证了缺失的实际数据后果；轨迹没有payload，不能进行原始UDP负载与DAT全量逐样本对拍。

## 能定位到哪里

生产实现SocketReceiver.cpp在recvfrom成功后立即写stage1，随后才调用统计观察及SourceCore::ingest。原始入口中已缺失的packet号未在后续到达；这些缺失不是先收到再被SourceCore丢弃。

本次源接收决定有1,643,723次Accepted和4次Duplicate，与1,643,727个数据报守恒；另有4个60字节ACK，总recvfrom为1,643,731。Disabled、RecentTrigger、OffsetOutside、InvalidCard均未出现。源Complete共46,904次；TriggerSwitch共120次，Timeout共4次，恰对应124个不完整卡触发。

所有46,900个参与同步的卡帧都有display/Ring回调返回true；publisher返回false，不能宣称外部发布成功，也不把它算作入口缺包。保存期间15,648个卡帧保存回调成功。没有输出队列满、同步队列驱逐、回调异常、过期交付或保存失败事件。未保存期间CardDisabled为保存关闭对应的正常分流，不当作采集丢包。回调返回不等于GPU完成，但足以排除这些记录中的队列丢弃解释。

这把直接缺失边界定位在recvfrom返回之前，尚不能把责任直接等同“网卡”。接收程序如果影响取包时机，可能影响更早的排队，但本日志没有足够的逐层队列/调度证据来证实该因果链，因此不将其作为根因。

接口InUcastPkts从18到1,643,751，增量1,643,733；比应用recvfrom只多2。接口InErrors/InDiscards及系统UDP InErrors一直0。计数方向不支持大量报文已经进入此接口统计后再被应用组包丢弃，但接口统计不是逐包抓取，有其它流量和边界差异，不能作为严格守恒证明；计数0也不能证明所有硬件路径无丢失。

多数运行期缺包表现为四卡同一trigger一起只收到前13/14包或前28/29包；三次开头也出现四卡共同的序号空洞。可确认故障具有跨卡共同特征，但没有分层证据确定共同故障发生在哪个组件。

## 已确认的启动过滤行为与显示口径

触发1四卡35包完整，源启动缓存约1秒空闲后主动过滤，未交付宿主。触发2四卡不完整，100ms超时结算后进入启动缓存，又被空闲清理。总startupFilteredCards=8、startupFilteredSync=1。

源码SourceCore::poll/clearStartup直接给出了此行为：未confirmed且距最近启动数据超过startupIdleMs=1000就清空启动缓存。启动确认在12:47:48.025、触发138时发生，释放51个完整同步触发缓存。后续两段首部异常发生时已confirmed，没有重新START或CONFIG，不是每个周期都执行一次启动门控导致。

首个物理触发是否丢包不能只看这个完整触发1：它是本run第一个可见报文触发，三段连续采集的各自首个可见触发确实不完整。源启动过滤和网络入口缺失必须分开统计。

CardStatusFormatting.h主状态显示“丢失”的数值是triggersPartial，单位是不完整触发，不是包数；tooltip才显示packetsDropped。新适配的packetsDropped只累加已见不完整触发的缺包，不补算完全不可见的83/76/89个触发。因此“丢失20”不代表只丢20包，也不覆盖全部序号空洞。无法从日志得知用户当时具体注视的控件，不能指定这是观察偏差的唯一原因。

## 停止定位的边界

当前证据足以否定中途零缺包，确认保存数据受损，区分入口缺失与启动过滤，并核实4001只是每段报文序号跨度。仍不足以给出唯一丢包根因或保证某项重构能修复。按用户要求，在此停止根因推断，不以缓冲区大小、线程优先级、USB网卡或GPU性能编造确定结论。

若继续调查，缺少的是同一次故障的接收侧更早层报文/丢弃证据与接收线程调度信息，以及本次触发计数语义或外部边沿计数。仅换一套应用组包逻辑无法补回本次从未进入recvfrom的报文；这不等于已经证明接收程序不可能间接影响丢包。
