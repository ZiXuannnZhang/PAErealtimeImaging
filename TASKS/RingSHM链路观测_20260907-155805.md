# Ring input SHM single-slot observability

## 1. Objective

对实时环扫 `ImagingController -> Ring SHM v2 -> ImagingSvc` 输入链路增加**严格限域的观测能力**，目标是回答一个工程问题：

> 当前单 slot Ring SHM 在真实生产速率下，producer 是否会在 ImagingSvc 消费前覆盖尚未消费的 block，以及 service 是否会因 ZMQ ready 消息积压而重复读取/跳读 SHM 中的当前最新 block？

本任务只做 instrumentation / observability，不修复协议，不改变数据所有权，不引入 backpressure。

必须能够观测并量化：

1. producer 提交 block 的序号与提交计数；
2. producer 写入前 slot 的 `block_ready` 与旧 `block_seq`，从而直接识别“覆盖尚未消费 block”的事件；
3. `ring_block_ready` 通知携带的 seq；
4. ImagingSvc 实际读取到的 SHM `block_seq` 与读取前 `block_ready`；
5. notify seq 与 SHM seq 不一致；
6. service 连续读取同一 SHM seq；
7. service 读取 seq 出现 gap；
8. producer submit 时间、consumer 读取时间、通知/排队延迟；
9. SHM lock+copy 时间；
10. 单 block ImagingSvc 总处理时间；
11. 按 session / reset epoch 汇总的累计计数。

最终目标是为后续是否需要 two-slot、ring buffer、显式 ACK 或 sequence ownership 提供实测证据。

**本任务不得直接实现上述协议重构。**

## 3. Problem / Evidence

### 3.1 当前 Ring SHM 是 single slot

`RingImagingShmHeader` v2 当前仍是 64-byte header，并已有：

```cpp
uint32_t block_seq;
uint8_t  block_ready;
```

后面只有一个 Raw Block 区，然后是 angles/channels 和输出 frame 区。

当前任务不允许修改这一布局。

### 3.2 Producer 当前行为

`ImagingController::submitRingBlock()` 当前大意为：

1. lock `m_ringSharedMemory`；
2. copy raw block；
3. copy angles；
4. copy physical channels；
5. 设置：

```cpp
h->block_seq   = blockSeq;
h->block_ready = 1;
```

6. unlock；
7. 发送：

```json
{"cmd":"ring_block_ready","seq":blockSeq}
```

当前 producer 在写入新 block 前**不检查/不记录**旧 slot 是否仍 `block_ready == 1`。

因此当前无法直接回答：producer 是否覆盖了尚未消费的 block。

### 3.3 Consumer 当前行为

`ImagingSvc::processMessage()` 收到：

```text
ring_block_ready
```

时目前直接调用：

```cpp
processRingPulse();
```

消息中的 `seq` 没有用于验证 SHM 内容。

`processRingPulse()` 随后：

1. lock Ring SHM；
2. 读取**当前 slot**中的 raw / angles / channels；
3. `h->block_ready = 0`；
4. unlock；
5. preprocess；
6. CUDA append；
7. snapshot；
8. 写 frame；
9. 通知 host。

因此若 ZMQ 已排队多个旧的 `ring_block_ready`，理论上多个通知可能对应同一个或更新后的 SHM slot。

### 3.4 当前 self-test 无法暴露该风险

现有 `ring_svc_selftest` 在每次写入 block 并发送 `ring_block_ready` 后，会等待对应 `ring_snapshot_ready`，再提交下一 block。

这实际上形成了 test-side serialization，因此它适合正常链路 regression，但不能证明真实 producer 在无 ACK 情况下不会覆盖 single slot。

本任务必须保留该正常 regression，同时新增能验证 observability 判定逻辑的自动化测试。

## 6. Recommended Design

允许等价设计，但建议采用以下低风险方案。

### 6.1 纯 bookkeeping helper

建议增加一个很小的、无 CUDA 依赖的 observability helper，例如：

```text
include/RingShmObservability.h
```

可以 header-only，也可以配套 `.cpp`。

职责仅包括：

- producer counters；
- consumer counters；
- seq continuity 判定；
- reset/start 时状态重置；
- anomaly flags；
- summary snapshot。

不要把 SHM I/O、ZMQ I/O、CUDA 或 Qt UI 逻辑塞进 helper。

这样可通过专用单元测试直接验证判定语义，而不依赖真实硬件或 GPU 调度时序。

### 6.2 Producer-side observation

在 `ImagingController::submitRingBlock()` 的现有 SHM lock 区间内，在覆盖 slot **之前**读取：

```text
previous_block_ready
previous_block_seq
```

然后执行原有 copy/write。

若：

```text
previous_block_ready != 0
```

必须：

- producer overwrite/single-slot busy counter +1；
- 记录 old seq 与 new seq；
- 产生带统一前缀的 anomaly diagnostic。

**不得因为该事件停止、等待、重试或丢弃当前 block。**

现有 write path 应继续执行。

建议 producer 维护：

```text
submitted_count
slot_busy_before_submit_count
last_submitted_seq
last_submit_interval_us
```

简单跨线程计数必须避免新 data race；若状态可能被不同线程访问，使用适当 atomic/既有同步，不要假设调用线程永远相同。

### 6.3 扩展现有 ready JSON，但不改变语义

保留：

```json
{"cmd":"ring_block_ready","seq":blockSeq}
```

允许增加**可选诊断字段**，例如：

```text
submit_index
submit_wall_us
```

要求：

- `cmd` 与 `seq` 字段保持；
- 额外字段只用于诊断；
- 旧格式只有 `cmd + seq` 时 service 仍能正常处理；
- 不增加等待回复语义；
- 不把任何 service telemetry 当作 ACK。

`submit_wall_us` 可使用同机可比较的 wall/system clock 微秒值，仅作诊断；实际单进程处理 duration 应使用 steady/monotonic clock。

### 6.4 Consumer-side observation

修改 `ImagingSvc::processMessage()`，读取 `ring_block_ready` 中的 notify seq，并把诊断 metadata 传给 `processRingPulse()` 或等价路径。

在 `processRingPulse()` 原有 SHM lock/copy 区间中，在清除 ready 之前记录：

```text
notify_seq
shm_seq = h->block_seq
ready_before_copy = h->block_ready
consumer_wall_us
```

然后仍按当前路径 copy raw/angles/channels，并：

```cpp
h->block_ready = 0;
```

不得因观测异常改变 copy/process 控制流。

至少维护：

```text
notification_count
consumed_count
notify_shm_mismatch_count
ready_zero_before_copy_count
duplicate_shm_seq_count
shm_seq_gap_count
last_consumed_shm_seq
copy_lock_us
process_us
```

判定：

#### notify/SHM mismatch

```text
notify_seq != shm_seq
```

直接记 anomaly。

这是“旧通知对应到了更新 slot”的强证据之一。

#### ready already zero

```text
ready_before_copy == 0
```

记 anomaly，但仍保持当前处理语义，不得 skip。

#### duplicate SHM seq

同一个 reset epoch 内：

```text
current_shm_seq == last_consumed_shm_seq
```

计数 duplicate。

#### seq gap

有上一 seq 且不是 duplicate 时，按 `uint32_t` 自然递增关系判断：

```text
current != last + 1
```

计数 gap。

不要把 `ring_reset` 后从较小 seq 重新开始误报为 gap。

### 6.5 Reset / session semantics

`start`：

- 新 session；
- 清 session counters；
- 清 continuity state。

`ring_reset`：

- 可以先输出上一 epoch summary；
- continuity state 必须 reset；
- 后续新的较小 blockSeq 不应产生 false gap；
- cumulative session counter 是否保留允许自行决定，但日志必须清楚区分 cumulative 与 epoch。

`stop`：

- 建议输出 final summary；
- 不要求持久化文件。

### 6.6 Timing

至少记录：

- producer submit wall timestamp；
- consumer observed wall timestamp；
- 估算 queue/notification latency；
- SHM lock + copy duration；
- `processRingPulse()` 整体 duration。

同一进程 duration 使用 monotonic/steady clock。

跨进程 wall-clock latency 仅作为诊断指标，不作为控制逻辑，不作为 pass/fail 的硬实时保证。

### 6.7 Telemetry output

需要一个稳定、可 grep 的前缀：

```text
[RingSHMObs]
```

推荐两层：

1. producer 在 host 侧对 slot-busy anomaly 立即 `svcStatus`/等价诊断输出；
2. service 通过现有 ZMQ PAIR 发送**非 ACK 的 telemetry message** 回 host，例如：

```text
cmd = ring_shm_observation
```

host 收到后只记录/emit diagnostic，不参与 block 提交许可。

service telemetry 至少应在以下时机产生：

- anomaly；
- 每固定数量 processed blocks 的 periodic summary（建议 32 或 50）；
- reset/final summary（如实现）。

不要每个 A-line 打日志。

日志/telemetry 至少包含足够字段，使后续硬件测试可以回答：

```text
submitted
slot_busy_before_submit
notifications
consumed
notify_shm_mismatch
ready_zero_before_copy
duplicate_shm_seq
shm_seq_gap
last_notify_seq
last_shm_seq
queue_delay_us
copy_lock_us
process_us
```

允许字段命名略有不同，但语义必须清楚。

### 6.8 Observer effect

instrumentation 不得显著改变 producer/consumer pacing。

要求：

- 不新增 blocking ZMQ send；
- telemetry 发送继续使用 nonblocking；
- 不新增磁盘同步写；
- 不在 hot path 格式化大型 payload；
- 不记录 raw samples；
- 不复制完整 block 仅用于诊断；
- anomaly/counter 之外尽量采用 periodic summary。

## 7. Implementation Freedom

Codex 可以自行决定：

- helper 的精确类名/结构体名；
- helper header-only 还是 `.cpp`；
- counters 使用 atomics 还是在明确单线程对象内使用普通整数；
- telemetry JSON 的附加字段具体名称；
- summary 间隔使用 32 或 50；
- `QElapsedTimer`、`std::chrono::steady_clock` 等 monotonic timing 实现；
- 单元测试采用仓库现有轻量断言风格或独立小 runner。

但以下不是 implementation freedom：

- 不得修改 SHM ABI；
- 不得新增 ACK/backpressure；
- 不得改变 ready ownership；
- 不得根据 anomaly 改变生产数据流；
- 必须能检测 producer overwrite-before-consume；
- 必须能检测 notify seq 与实际 SHM seq mismatch；
- 必须能检测 ready=0、duplicate、gap；
- reset 后不得 false gap；
- 必须有自动化测试；
- 必须实际执行现有 ring service regression。

## 9. Required Tests

新增 `Ring SHM observability` 专用自动化测试，至少覆盖以下语义。

### T1. Producer clean submit

输入：

```text
previous_ready = 0
previous_seq = N
new_seq = N+1
```

验证：

- submitted +1；
- slot-busy/overwrite counter 不增加；
- 不报告 anomaly。

### T2. Producer overwrite-before-consume detection

输入：

```text
previous_ready = 1
previous_seq = N
new_seq = N+1
```

验证：

- submitted +1；
- slot-busy counter +1；
- anomaly 记录 previous/new seq；
- detector 本身不产生“drop/retry/wait”动作。

### T3. Consumer normal match

```text
notify_seq == shm_seq
ready_before_copy == 1
```

连续 seq 正常时：

- mismatch=0；
- ready_zero=0；
- duplicate=0；
- gap=0。

### T4. notify/SHM mismatch

```text
notify_seq = N
shm_seq = N+1
```

验证 mismatch counter +1。

### T5. ready already zero

```text
ready_before_copy = 0
```

验证 ready-zero counter +1。

不得把该单元测试设计成“consumer 应跳过 block”，因为生产语义本任务不改变。

### T6. duplicate SHM seq

同 epoch 连续观测：

```text
10, 10
```

验证 duplicate +1，且不要同时错误计算为正常递增。

### T7. SHM seq gap

同 epoch 连续观测：

```text
10, 12
```

验证 gap +1。

### T8. Reset continuity

观测：

```text
30
ring_reset
0
```

验证 reset 后 `0` 不被报为 gap/rollback anomaly。

### T9. uint32 continuity boundary

如 helper 使用 `uint32_t` 自然递增，应覆盖：

```text
0xFFFFFFFF -> 0
```

不误报 gap。

这不是当前常规 blockSeq 运行范围要求，只用于避免观测器自身产生算术边界 bug。

### T10. Optional diagnostic fields backward compatibility

验证 service/message parser 至少能接受原格式：

```json
{"cmd":"ring_block_ready","seq":1}
```

即使没有新增 timestamp/index 字段，也不得 crash、拒绝或改变处理语义。

### T11. SHM ABI guard

测试或 compile-time guard 确认：

```text
sizeof(RingImagingShmHeader) == 64
```

并确认本任务 diff 中 `ImagingSharedMemory.h` 没有变化。

### T12. Normal ring service regression

使用当前可用 `testdata/14.dat` 与 external `ImagingSvc.exe` 运行现有 `ring_svc_selftest` 正常模式。

要求：

- exit code 0；
- 双波长链路正常；
- 不因 instrumentation 改变 reconstruction output path；
- 在 selftest 的逐块 wait 模式下，预期不出现 notify/SHM mismatch、ready-zero、duplicate/gap anomaly；
- 若 periodic summary 输出，应记录其 counters 作为证据。

### T13. Detection-path deterministic test

必须有一个**不依赖真实硬件调度概率**的测试，证明下面的历史风险形态能被观测器判定：

```text
notification says seq A
single SHM slot currently contains seq B
A != B
```

推荐通过 pure helper/unit test 构造，不要求为了触发它在生产代码加入 sleep。

如果 Codex 选择给 `ring_svc_selftest` 增加专用 burst mode，也可以，但不得以不稳定竞态测试替代确定性单测。
