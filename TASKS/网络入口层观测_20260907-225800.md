# Pre-recvfrom / network-interface ingress observability

## 1. Objective

在不改变采集、组包、Ring、保存和重建行为的前提下，为 Windows 实机采集链路补齐 `recvfrom()` 之前和紧邻 `recvfrom()` 的分层观测能力，以回答下一轮实机测试的核心问题：

> 当前大量 UDP 缺失究竟发生在 FPGA/物理网络/NIC/Windows NDIS-IP-UDP 栈进入应用之前，还是 packet 已经到达应用后，因为接收时序、跨 trigger 乱序或组包拒绝而没有进入最终 trigger？

本任务只做 **observability / instrumentation**，不修复两个已知次级组包风险，不调优 NIC，不改变线程/队列/协议行为。

必须新增三层可关联证据：

1. **Windows 网络接口 / IP / UDP 栈层**：相关采集接口的累计接收、丢弃、错误及对应时间窗口 delta；
2. **`MultiPortReceiver` 入口层**：`select/recvfrom` 调度、burst/drain、socket 错误以及每卡原始 `triggerSeq/packetSeq` 接收顺序异常计数；
3. **组包拒绝观测层**：只统计已经进入应用、但随后因 stale-trigger / duplicate / packet offset out-of-range 等原因未进入有效组包结果的数量，用于直接判断两个次级风险是否实际触发。

所有新增结果必须进入 DiagnosticRecorder 导出 ZIP，下一次实机测试后无需额外调试器即可从日志重建时间关系。

UI 已经通过上一轮实机验证，本任务 **不得继续修改前端状态栏或 tooltip**。

## 3. Problem / Evidence

### 3.1 上一轮实机已排除应用内部 batch queue 大量丢包

最新 4 卡实机日志最终逐卡均表现为：

```text
socketPacketsReceived == processorPacketsDequeued
batchBoundaryDiscards == 0
inputQueueDepth == 0
```

示例：

```text
卡1  socketPacketsReceived=344660  processorPacketsDequeued=344660
卡2  socketPacketsReceived=344688  processorPacketsDequeued=344688
卡3  socketPacketsReceived=344690  processorPacketsDequeued=344690
卡4  socketPacketsReceived=344687  processorPacketsDequeued=344687
```

但对应 `packetsDropped` 仍约 7.55 万包/卡，`triggersPartial` 大量增加。

因此已能排除：

```text
recvfrom() 成功 -> enqueue -> DataProcessor dequeue
```

这一段存在大量静默丢包。

### 3.2 实机缺失与理论 trigger 包数高度闭合

该次实机配置约为：

```text
acqTime = 50 us
sampleInterval = 4 ns
A+B, 32 bit/channel
UDP payload = 1440 bytes
```

理论每 trigger 为 70 个 UDP packet。

卡1整场：

```text
344660 received + 75550 inferred missing = 420210 = 6003 * 70
```

其它卡只有 0~2 包量级边界差异。

该守恒关系说明绝大多数 inferred missing packet 没有在当前应用入口计数中出现；如果大量 packet 已经进入 WinSock、随后才因组包策略被丢弃，则 `socketPacketsReceived + packetsDropped` 应显著大于理论总包数。

因此目前更怀疑 `recvfrom()` 之前的 FPGA/network/NIC/driver/NDIS/IP/UDP ingress path。

### 3.3 四卡缺失高度同步

四卡大量 partial trigger 在物理 trigger 位置和缺失数量上高度同步，常见模式包括多卡同时缺 22、7、40、55 等近似相同数量。

这更像四路共有的上游 ingress/microburst/host receive 资源问题，而不像四个独立 DataProcessor 随机同时失败。

### 3.4 Imaging 开启后缺失率显著恶化

上一轮近似三段实机结果显示：

```text
仅采集              ~2.3% missing
开启实时成像        ~28% missing
实时成像 + 保存     ~24% missing
```

该现象还不是严格因果证明，但必须通过下一轮观测判断：

- OS/NIC interface discard/error 是否随成像负载同步增加；
- Windows IP/UDP stack error/discard 是否增加；
- receiver thread 是否出现长 scheduling gap 或异常大的 drain burst；
- 如果 OS 层 counters 不增加，应用入口 `packetSeq` 是否已经可见 reorder/gap/reject。

### 3.5 两个次级风险仍存在，但本任务不修

风险 A：DataProcessor 只有单 trigger assembly buffer；新 trigger 先到会立即 flush 旧 trigger，后到旧包随后被 stale-trigger 逻辑丢弃。

风险 B：PacketAssemblyBuffer 当前以“第一到达 packetSeq”作为 `m_basePacketSeq`；若同 trigger 内首到包不是最早序号，后到的较小 packetSeq 可能计算成超大 offset 并被拒绝。

源码风险真实存在，但最新实机守恒关系不支持它们是当前数万包缺失的主因。

本任务必须**只观测它们是否真实触发，不得修复其行为**。

## 6. Recommended Design

允许等价实现，但必须提供以下可验证语义。

### 6.1 Windows interface ingress sampler

优先复用/扩展现有 `NetworkDiagnostics`，它已经使用：

```text
GetAdaptersAddresses
GetIpForwardTable2
GetIpNetTable2
```

建议新增一个轻量 runtime sampler，而不是在每个 packet hot path 调 Windows API。

#### 6.1.1 识别真正承载采集流量的接口

针对每个 `targetIP`，使用 Windows routing API（推荐 `GetBestRoute2`，等价方案可接受）解析：

```text
target IP -> InterfaceIndex / InterfaceLuid
```

需要导出：

```text
interfaceIndex
interfaceLuid（必须无精度损失，例如 decimal string）
friendlyName
description
local IPv4
operationalStatus
MTU
receiveLinkSpeed
transmitLinkSpeed
```

如果 4 个 target 全部走同一接口，应明确记录 `sharedByTargets=[...]`。

不得仅根据 friendly name 猜接口。

#### 6.1.2 per-interface counters

使用标准 Windows IP Helper API（推荐 `GetIfEntry2` / `MIB_IF_ROW2`）读取至少：

```text
InOctets
InUcastPkts
InNUcastPkts
InDiscards
InErrors
InUnknownProtos
OutOctets
OutUcastPkts
OutNUcastPkts
OutDiscards
OutErrors
```

要求同时记录：

- absolute cumulative value；
- 相邻 runtime snapshot 的 delta；
- sample timestamp / monotonic timestamp；
- API error status。

64-bit lifetime counters 必须以不会损失整数精度的 JSON 表达方式导出。

这些 counters 应命名为 **Windows interface counters**，不得在日志中直接称为“硬件 NIC drop”，因为其精确归属依驱动实现而定。

### 6.2 Windows IP/UDP stack counters

为了继续分层，建议同时周期采样 IPv4 system counters：

- `GetIpStatisticsEx(AF_INET)`；
- `GetUdpStatisticsEx(AF_INET)`。

至少导出可获得的：

```text
IP:
  InReceives
  InHdrErrors
  InAddrErrors
  InUnknownProtos
  InDiscards
  InDelivers

UDP:
  InDatagrams
  NoPorts
  InErrors
  OutDatagrams
```

同样记录 absolute + delta。

这些是 system-wide counters，导出字段和 summary 必须明确标注 `scope=system_ipv4`，不得误解为单独某张卡的数据。

如果 API/字段在当前工具链不可用，保留 `status=unavailable/errorCode`，不要失败采集。

### 6.3 MultiPortReceiver scheduling / burst observability

在不改变现有接收算法的情况下，增加低成本原子/线程本地累计统计。

每个 receiver group 至少记录：

```text
selectWakeups
selectTimeouts
selectErrors
recvHardErrors             // 不包含 WSAEWOULDBLOCK
recvWouldBlockTerminations // 正常 drain 结束
maxDrainPackets            // 一次 socket drain 最大 datagram 数
maxDrainDurationUs         // 一次 drain 最大耗时
maxReceiverLoopGapUs       // receiver 可运行循环/有数据 drain 起点之间的最大 gap，定义写清
```

如果适合，可按 card/socket 记录 `maxDrainPackets`，因为四卡同步 burst 是当前重要怀疑点。

时间采样应限制在 drain-cycle 粒度，不要求对每包调用高成本 wall-clock API。

### 6.4 Per-card raw receive-order sequence observability

在 packet header 已解析、`socketPacketsReceived++` 附近做**纯观测**。

不要先假设 `packetSeq` 是 trigger 内序号还是全局序号；当前源码注释存在不一致。

因此首轮观测建议只在“同一个 triggerSeq 内”判断 packetSeq 接收顺序：

```text
sameTriggerForwardGapEvents
sameTriggerForwardGapPackets
sameTriggerBackstepEvents
sameTriggerDuplicateSeqEvents
lastTriggerSeq
lastPacketSeq
```

定义：

- 同 trigger 内 `packetSeq` 比上一个接收值前进 >1：记录 forward gap，但只称 `receive-order gap`，不得直接称 network loss；
- 同 trigger 内 packetSeq 下降：记录 backstep/reorder；
- 同 trigger 内相同 packetSeq：记录 duplicate；
- uint16 wrap 必须显式处理；
- trigger 切换时不要把 packetSeq reset/continuity 误算为 gap。

另外增加：

```text
crossTriggerLateArrivalEvents
```

仅表示在已经观察到更“新”的 trigger 后，又收到更“旧”的 trigger packet；必须采用现有 uint16 trigger wrap-safe 比较或独立 helper 测试，不得改变接收/组包结果。

### 6.5 Application-side rejection observability

本任务允许在 DataProcessor / PacketAssemblyBuffer 附近增加**只读结果分类计数**，用于下一轮直接判断两个次级风险是否真实触发。

至少区分：

```text
staleTriggerPacketsDiscarded
assemblyDuplicatePackets
assemblyOffsetOutOfRangePackets
```

其中：

- `staleTriggerPacketsDiscarded`：DataProcessor Step 1 已经 `continue` 的旧 trigger/迟到 packet 数；
- `assemblyDuplicatePackets`：PacketAssemblyBuffer 因 bitmap 已存在而拒绝；
- `assemblyOffsetOutOfRangePackets`：`packetSeq - basePacketSeq` 结果不在 buffer 范围而拒绝。

允许 Codex 采用 enum return/result struct、旁路 tracker 或其它最小侵入方式，但必须证明：

> 对同一输入 packet，修复前和本任务后的 accepted/rejected 行为完全一致；新增代码只把既有结果分类计数。

如果修改 `PacketAssemblyBuffer::insertPacket()` 签名，会影响调用处，必须增加 deterministic regression 证明 output/receivedCount 行为不变。

### 6.6 Diagnostic export

#### 6.6.1 `network.json`

运行期间每约 2 秒（允许与现有 runtime card snapshot 同节奏）记录一份 network ingress snapshot，至少包含：

```text
kind = runtime_ingress
relevantInterfaces[]
interfaceCounters absolute/delta
systemIpv4Counters absolute/delta
systemUdpCounters absolute/delta
receiverGroups[]
```

不要覆盖现有 start/config network snapshots；应保留完整 history。

#### 6.6.2 per-card snapshot fields

现有逐卡 runtime fields 在保留全部原字段基础上增加至少：

```text
sameTriggerForwardGapEvents
sameTriggerForwardGapPackets
sameTriggerBackstepEvents
sameTriggerDuplicateSeqEvents
crossTriggerLateArrivalEvents
staleTriggerPacketsDiscarded
assemblyDuplicatePackets
assemblyOffsetOutOfRangePackets
```

以及如采用按卡的 receiver burst stats，也一起写入。

#### 6.6.3 `summary.txt`

只增加一个简短“网络入口观测”汇总即可，至少列：

- 采集接口名称/index；
- 最终 interface InDiscards/InErrors delta（若可用）；
- system UDP InErrors delta；
- 每卡 socket received / processor dequeued / raw receive-order gap / stale / assembly reject totals。

不要把 summary 当 machine-readable 唯一来源；完整证据必须在 JSON。

### 6.7 Hot-path overhead

这次观测本身不能制造新的丢包。

要求：

- packet hot path 只做少量整数/atomic/线程本地更新；
- Windows interface/IP/UDP API 只能在定时器/后台 snapshot 路径调用；
- 不允许每包 `QJsonObject`、QString format、DiagnosticRecorder enqueue 或磁盘 I/O；
- anomaly event 如确实需要文本，只能限频/采样，主证据必须是 counters。

## 10. Regression Baseline

本任务必须保留上一项已经实机确认有效的行为：

