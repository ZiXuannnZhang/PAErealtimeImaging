# DataProcessor batch boundary fix and acquisition-status diagnostics

## 1. Objective

修复 100 Hz 实机采集调查中已经确认的 `DataProcessor` 批处理边界静默吞包缺陷，并补齐可以区分接收层、处理层与批处理边界行为的采集计数器；同时按用户确认的 UI 方案简化主窗口逐卡状态显示，并确保新增计数器进入诊断导出包。

本任务的核心目标：

1. 修复 `DataProcessor::run()` 当前 512 batch 边界会成功 dequeue 第 513 个包、但不进入处理体的确定性缺陷；
2. 新增三个明确分层的累计计数器：
   - `socketPacketsReceived`：WinSock 成功接收并准备送入 processor 的有效 UDP 数据包数；
   - `processorPacketsDequeued`：DataProcessor 从 `m_inputQueue` 成功 dequeue 的包数；
   - `batchBoundaryDiscards`：已经 dequeue、但仅因为 batch 边界而未进入处理逻辑的包数；修复后正常运行必须保持 0；
3. 保留所有既有计数器与统计语义；
4. 主窗口逐卡常驻文本只保留“丢失”状态；
5. 当前 UI 中 `packetsDropped` 对应文案从“丢弃”改为“缺失”；
6. `缺失 / 处队 / 存队` 及其他详细采集统计放入该逐卡状态标签的 tooltip，鼠标悬停时查看；
7. 新增三个计数器必须进入 DiagnosticRecorder 的逐卡运行快照，并能够在导出的诊断 ZIP 中直接读取。

本任务**不处理**已调查到的第二层潜在问题，例如跨 trigger 乱序、单 trigger assembly buffer 过早 flush、`PacketAssemblyBuffer` 首包作为 packet-seq base 的乱序风险。这些应在本缺陷修复并完成下一轮实机复测后单独评估。

## 3. Problem / Evidence

### 3.1 已确认的 512 边界缺陷

当前：

```cpp
int count = 0;
while (m_inputQueue.try_dequeue(pkt) && count++ < PROC_BATCH_SIZE) {
    ...
}
```

且：

```cpp
constexpr int PROC_BATCH_SIZE = 512;
```

C++ `&&` 左到右求值导致：

1. 第 513 次先执行 `try_dequeue(pkt)`；
2. 若队列非空，该包已被成功移除；
3. 随后 `count++ < 512` 为 false；
4. 循环退出；
5. 第 513 个包未进入处理体，也未重新入队。

因此在 processor backlog 足够深时，每个满 batch 都可能静默吞掉 1 个真实收到的 UDP 包。

这是真实的软件内部数据丢失，不是单纯 UI 统计假象。

### 3.2 当前 UI 四项的实际语义

当前逐卡状态中：

- `丢失` -> `triggersPartial`：不完整 trigger 的累计数；
- `丢弃` -> `packetsDropped`：根据组包缺口推断出的缺失 UDP 包累计数；
- `处队` -> `inputQueueDepth`：DataProcessor 输入队列近似深度；
- `存队` -> `saveQueueDepth`：FileSaver 队列近似深度。

`丢失` 与当前文案“丢弃”不是两种独立故障：一个 trigger 少 1 个包时，通常会同时表现为 `triggersPartial +1` 和 `packetsDropped +1`。

因此 UI 文案必须把 `packetsDropped` 从“丢弃”改为更准确的“缺失”。

### 3.3 当前 `packetsReceived` 不是 socket 层计数

现有 `CardStats::packetsReceived` 在 `DataProcessor` 成功进入处理循环体后增加，因此它不能证明 WinSock 实际收到了多少包，也无法识别“socket 已收到但 processor batch 边界吞掉”的场景。

本任务新增三个分层计数器就是为了建立可核验的守恒关系。

### 3.4 当前诊断导出缺少采集运行统计

现有 DiagnosticRecorder 能导出 event、network/settings snapshot、card snapshot 与 recorder 自身 drop counters，但实机导出中没有保存本次运行的 UDP/trigger/processor queue 统计，因此无法仅凭导出 ZIP 回放“丢失/缺失/处队/存队”的现场数值。

本任务必须把新增三个计数器和必要的既有采集统计写入逐卡运行快照，确保下一次实机导出可以直接诊断。

## 6. Recommended Design

允许等价实现，但必须满足以下可验证语义。

### 6.1 修复 batch loop

推荐把循环条件改成“先检查 batch quota，再 dequeue”：

```cpp
int count = 0;
while (count < PROC_BATCH_SIZE && m_inputQueue.try_dequeue(pkt)) {
    ++count;
    ...process pkt...
}
```

或任何严格等价、不会在 quota 用尽后继续 dequeue 的写法。

关键不变量：

> 当一个 batch 已处理 512 包时，第 513 包必须仍留在 queue 中，由下一轮处理；不能从 queue 消失。

### 6.2 三个新增计数器

建议加入 `CardStats` / `CardStats::Snapshot`，采用 `std::atomic<uint64_t>`：

```text
socketPacketsReceived
processorPacketsDequeued
batchBoundaryDiscards
```

#### `socketPacketsReceived`

精确定义：

- `recvfrom()` 返回一个可解析的数据包；
- `recvd >= UDP_HEADER_BYTES`；
- 已解析 header，并即将调用对应 `DataProcessor::enqueuePacket(pkt)`；
- 此时 +1。

不要把 select wakeup 空包、短包、bind/control/feedback 包计入。

若对应 processor 指针不存在，则不要假装成功送入 processor；实现应在回执中明确计数边界。

#### `processorPacketsDequeued`

每一次：

```text
m_inputQueue.try_dequeue(pkt) == true
```

时 +1。

它统计 processor 实际从输入队列取得的包，不等同于 trigger 完整数。

现有 legacy `packetsReceived` 继续保留。若修复后它仍在同一实际处理点更新，则正常情况下应与 `processorPacketsDequeued` 保持一致；不要删除 legacy 字段。

#### `batchBoundaryDiscards`

精确定义：

> 包已被 processor queue 成功 dequeue，但仅由于 `PROC_BATCH_SIZE` quota 已耗尽而没有进入处理逻辑。

正确修复后该路径原则上不应再发生，因此实机与 deterministic regression 中必须为 0。

这个计数器是防回归 sentinel，不允许为了让其非零而保留旧 bug。

### 6.3 守恒关系

在无 stop/race 边界的稳定采集窗口，应能够观察：

```text
socketPacketsReceived >= processorPacketsDequeued
batchBoundaryDiscards == 0
```

其差值应主要反映尚未被 processor 消费的 queue backlog / 短暂 in-flight，而不是静默消失的数据。

不要把三个计数相加成“总丢包”。

### 6.4 主窗口简化显示

用户已确认：

**逐卡常驻状态只显示“丢失”。**

推荐格式：

```text
卡1 | 丢失: 0
```

其中“丢失”仍使用：

```text
triggersPartial
```

不允许把 `packetsDropped` 改成“丢失”。

鼠标悬停在对应逐卡状态标签时，tooltip 至少显示：

```text
触发完成: <triggersComplete>
缺失: <packetsDropped>
处队: <inputQueueDepth>
存队: <saveQueueDepth>
Socket接收: <socketPacketsReceived>
Processor出队: <processorPacketsDequeued>
批边界丢弃: <batchBoundaryDiscards>
速率: <recvMbps> Mb/s
触发率: <triggerHz> Hz
```

已有 `saveQueueDiscards`、`triggersDiscarded` 等详细指标也应保留；可放入 tooltip，不应继续把主标签撑成长文本。

前端中原：

```text
丢弃: <packetsDropped>
```

必须改为：

```text
缺失: <packetsDropped>
```

这里是 UI 文案变更，不要求破坏性重命名底层 `packetsDropped` API。

### 6.5 DiagnosticRecorder / 导出 ZIP

新增三个计数器必须进入导出日志，而且是**采集运行统计**，不能塞进 DiagnosticRecorder 自身 `dropCounters`。

建议在现有 per-card `CardSnapshot.fields` 中加入稳定 machine-readable keys：

```text
socketPacketsReceived
processorPacketsDequeued
batchBoundaryDiscards
```

同时建议把本次问题定位所需的既有字段一起纳入运行快照：

```text
packetsReceived
packetsDropped
triggersComplete
triggersPartial
triggersDiscarded
saveQueueDiscards
inputQueueDepth
saveQueueDepth
recvMbps
triggerHz
packetLossRate
```

要求：

1. 采集运行期间应周期性记录逐卡 runtime snapshot，频率不要求和 UI 每次刷新完全一致，但不得高频刷爆 DiagnosticRecorder；推荐 2~10 秒量级；
2. 在停止测量/停止监听和导出前，必须有机制记录一次最新逐卡 snapshot，使用户点击导出后 ZIP 至少包含接近导出时刻的最终计数；
3. 导出 ZIP 中 `network.json`（或现有 card snapshot 所属正式导出文件）必须能直接找到以上三个新 key；
4. `SUMMARY.txt` 是否增加简要采集统计可由 Codex决定，但 machine-readable JSON 是硬要求；
5. 现有 DiagnosticRecorder `dropCounters` 必须保持原意义与字段，不得被新计数器覆盖。

如选择增加新的专用 `acquisition.json`，必须说明理由，并保证旧 `network.json`/manifest 格式兼容；默认优先复用现有 CardSnapshot 机制，减少导出格式扩张。

## 9. Required Tests

必须覆盖以下测试。

### T1 — deterministic 513 boundary

构造至少 513 个待处理 packet，使 processor queue 在一个 batch 开始时深度 > 512。

验证第一轮 batch 后：

```text
processorPacketsDequeued 增加恰好 512
batchBoundaryDiscards == 0
至少 1 个 packet 仍留在 queue / 可在下一轮处理
```

第二轮后剩余 packet 被正常 dequeue/处理。

不得只测试 `count < 512` 的独立表达式；必须经过真实 queue drain 逻辑或与生产代码共用的 helper。

### T2 — exact batch

初始队列恰好 512 包：

- 全部处理；
- queue 为空；
- `processorPacketsDequeued += 512`；
- `batchBoundaryDiscards == 0`。

### T3 — below batch

511 或更少 packet：全部处理，无残留，无 batch discard。

### T4 — multi-batch conservation

例如 1025 或更大 packet 流：

- 最终全部被处理；
- 无静默丢包；
- 每轮最多处理 512；
- `batchBoundaryDiscards == 0`。

### T5 — socket counter boundary

验证只有成功 `recvfrom` 且满足有效数据包最小长度、实际进入 data enqueue path 的包才计入 `socketPacketsReceived`。

短包/停止唤醒包不得计入。

如难以对真实 WinSock 写稳定单元测试，可抽取最小纯 bookkeeping seam，但必须证明生产 `MultiPortReceiver` 使用同一计数路径。

### T6 — legacy counters preserved

仍存在，正常场景语义未被新计数器替换。

### T8 — UI tooltip
