# 实时成像对采集影响：架构与实机对照

2026-09-11。只读审查当前诊断构建对应源码40859a18c3ba026ff99dd2a5196923e67fc251f0及已导出实机轨迹，未修改产品。

## 判断

成像开启确实引入额外同进程线程、内存复制、跨进程共享内存和GPU/显示工作，当前架构不是完全资源隔离。但现有证据不能确认“开启实时成像导致接收丢包”。本轮缺失发生在第一个重建块提交之前；稳态重建持续运行时随后3974个有效触发均完整，不支持持续重建吞吐不足或重建直接阻塞接收的解释。

用户补充保存轮不开成像、非保存轮开成像，日志与之吻合。两轮还同时改变了保存状态，并且先后顺序、空闲状态和源启动确认状态不同，不是只切换成像的单变量对照。

## 当前实际调用链和线程边界

1. SocketReceiver接收线程：select → 逐socket recvfrom → 原始轨迹 → ingress统计 → coreMutex → SourceCore解析/组包/跨卡同步。
2. SourceCore在接收调用栈内构造卡帧、分配/拷贝字节，并调用pushCard和pushSync；这两个入口短暂锁住输出队列。因此接收并非纯粹读socket后立刻返回。
3. OutputWorkers的cardWorker负责保存；syncWorker负责完整跨卡组的转换、普通波形显示和Ring馈送。消费者先弹出队列并释放cardMutex/syncMutex，再执行sink；GPU和磁盘操作不在这些队列锁内。
4. HostOutput::consumeSync将各卡bytes转换成float，DataProcessor::deliverAssembled执行降采样、DisplayBuffer更新、全分辨率副本更新、ringFeedSink。
5. MainWindow::ringFeedSink复制A/B数组，短暂锁Ring馈送队列；RingFeedWorker弹出后释放锁，再调用RingBlockAssembler。组满50触发后转换QVector并调用ImagingController::submitRingBlock写共享内存。
6. 独立ImagingSvc进程取块、预处理/CUDA重建、写两幅图像快照；宿主另一个Ring图像worker读快照，通知UI显示。

重建服务共享内存锁可能拖慢Ring馈送/图像worker，但这些worker处理共享内存时不持有接收侧syncMutex或coreMutex。因此没有看到“GPU重建期间持接收锁阻塞recvfrom”的直接调用链。异步隔离减少直接阻塞，不等于隔离CPU、缓存、内存分配器、驱动和物理内存。

## 已确认架构问题及其影响范围

### A. 成像数据有不必要的全量复制

DataProcessor在displayAndRing路径无条件更新DisplayBuffer全分辨率副本；环形成像又走独立ringFeedSink，后者复制全部卡的A/B数据，未在复制前筛掉未启用成像通道。RingBlockAssembler在入参处才忽略未启用通道。

活跃通道还经历pending行复制、块buffer复制、std::vector到QVector复制、共享内存复制。不开成像时syncWorker和普通显示转换仍然执行，不能把syncWorker所有工作当成成像开关新增工作。

这些是明确的CPU/分配/内存带宽开销，适合优化；本次没有测到足以证明它们引发接收丢包的因果证据。

### B. 图像快照很大，跨进程和UI资源不独占

现场nx=3600，单幅float图像3600²×4=51,840,000字节；两幅共103,680,000字节。ImagingSvc每块生成两幅全分辨率快照并写入共享内存；宿主每次processRingFrame再复制这两幅到显示缓冲。宿主双缓冲占207,360,000字节，尚不含共享内存、GPU工作区、子进程数组和UI显示内存。不能把该估算当成现场实际驻留内存。

这类资源竞争是成像可能间接影响接收的路径。但本轮第一幅新数据图像在缺失发生之后才可能产生，不能用它解释已经发生的首部缺失。服务初始化、预分配或GPU上下文等影响未被完整监测，仍未知。

### C. 队列丢弃被ringReturn=true掩盖

ringFeedSink返回void：停止时直接return，2048项队列满也直接return，没有专门丢弃计数。DataProcessor调用后无条件result.ring=true。于是stage7的ringReturn=true只能证明回调返回，不能证明入队、组块或重建完成；成像关闭时它也可能为true。

这是实际可观测性缺陷。Ring队列溢出会丢成像数据，但发生在UDP接收之后，不能解释本次stage1完全未出现的25次有效触发。此前“无输出队列丢弃”的结论仅适用于有记录的PAimage输出队列，不能扩展到未计数的RingFeed队列。

### D. 调度隔离不完整

接收线程请求HIGHEST；syncWorker、RingFeedWorker、Ring图像worker请求ABOVE_NORMAL。ImagingSvc代码请求BELOW_NORMAL并排除逻辑CPU0/2，但新接收线程不绑核，因此这不构成接收专用核。现场未拿到调度保护应用结果，不宣称请求全部生效。

这是共享资源边界，不是发现优先级设置本身有错，也不是建议立即恢复旧绑核。没有调度轨迹不能判断线程是否被抢占、DPC/ISR是否拥塞。

## 时序对照与限制

独立脚本imaging_timing_check.py按原始入口时间选取阶段，与相交timing记录对照。成像轮从首数据到第一块所需50个完整触发期间，保留的drain最大约0.0716ms、syncWorker最大0.8063ms、select最大2.9154ms。core等待/ingest等没有达到详细记录的0.5ms门槛。保存轮开头syncWorker最大2.834ms、保存worker最大4.4398ms；保存轮有效采集仍完整。不能将这些不等长窗口最大值用作性能基准。

记录只覆盖已设计的区间及门槛以上细项，LoopGap并非完整取包间隙，TimingWriter::observe自身也有区间外开销。没有明确的大锁等待不代表已经排除所有程序/系统停顿。没有系统调度、GPU初始化和页面错误轨迹，不能继续确定根因。

50微秒两个缺包段早于这次10:28后的成像服务启动日志；本附件没有显示它们运行当时启动ImagingSvc。单纯选择“环形模式”不等于开启实时重建。不能把50微秒的持续缺包无依据归到后来启动的成像上。

## 下一步判断

不建议先做大规模成像重构来承诺修复采集。优先单变量复核：保持保存关闭、采集参数/诊断级别/轮间空闲相同，成像关→开→关重复多轮；另做保存开关对照，避免两个变量同时变化。记录服务启动到第一轮触发的等待时间，区分刚启用成像与已运行稳定后开始新轮。所有实验仅接收侧操作。

最小监测补充应为：RingFeed入队/满丢/停止拒收/峰值/等待、源同步worker分段耗时、真实成像enabled与svcReady事件、首块提交/开始处理/完成/首帧显示、成像初始化区间；同时取得接收线程调度与网络分层轨迹。将ringReturn替换为明确交付结果可修正误判，但它不是采集丢包修复。

优化多余复制、只处理启用通道、按需生成显示副本、缩小显示快照有合理架构依据，但本报告不把它们作为已证实的根因修复，不执行产品修改。
