## 2. 已确认的当前竞态

当前生产 receiver 主循环本质顺序：

```text
processSessionCommands()
-> build fdset
-> select(..., 1 ms)
-> readable
-> drainSocket()
-> dispatchDatagram()
```

当前 Start transaction 对每张卡的顺序本质为：

```text
send Start(card)
-> local send succeeds
-> commitCardSession(card)
```

`commitCardSession()` 通过 receiver command queue 执行，不是在 controller caller 上立即改变 receiver-owned state。

因此以下 interleaving 合法：

```text
T0 card = ARMED
T1 controller sendto(Start) returns success
T2 FPGA/new-session packet may arrive immediately
T3 card UDP socket becomes readable; select returns
T4 receiver drains the socket
T5 CommitCard command has not yet been applied
T6 dispatchDatagram sees ARMED
T7 packet increments sessionBoundaryPacketsDiscarded and is discarded
T8 next receiver loop applies CommitCard -> RUNNING
```

本任务要关闭的是上述**软件可控窗口**：

> 某卡本地 Start send 已成功以后，在 receiver 的“允许该卡进入新 session”状态尚未完成同步交接期间，已经到达该卡 socket 的新 session 数据不能被 receiver 主循环主动 `recvfrom()` 后作为 boundary packet 丢弃。

当前 `session_boundary_receiver_test.cpp` 主要覆盖的是：

```text
prepare -> arm -> commit -> inject new packet
```

以及同类 100-cycle 顺序；它没有构造：

```text
Start success
-> admission completion still pending
-> socket already readable
```

因此本轮必须新增该精确窗口的 deterministic regression。

## 3. 目标同步模型

实现必须建立 **receiver-owned per-card START_FENCE_HOLD**，或一个在以下全部语义上等价、能够由生产控制流和测试直接证明的机制。

推荐状态：

```text
DISARMED
PREPARING
ARMED
START_FENCE_HOLD
RUNNING
```

### 3.1 每卡 Start 的生产顺序

对每一张 target card：

```text
A. receiver.beginCardStartFence(sessionToken, card)
   -> receiver-owned command
   -> validate ARMED + token + card ownership
   -> enter START_FENCE_HOLD
   -> quiesce this card's pre-Start socket backlog to WSAEWOULDBLOCK
   -> return only after HOLD semantics are effective

B. controller send Start(card)

C1. local Start send succeeds:
    receiver.completeCardStartFence(sessionToken, card, SUCCESS)
    -> validate token/card/HOLD
    -> publish RUNNING for this card first
    -> only after RUNNING may normal receive/drain resume for this card

C2. local Start send fails:
    receiver.completeCardStartFence(sessionToken, card, FAILURE)
    -> do not publish RUNNING
    -> leave the card in a closed admission state
    -> quiesce/clear any HOLD backlog without raw-order observation or processor admission
    -> transaction follows existing rollback/teardown path
```

API 名称可调整，但生产调用顺序和状态语义必须等价。

### 3.2 START_FENCE_HOLD 的核心语义

HOLD 期间，对该 card：

```text
socket may receive datagrams into Windows UDP backlog
receiver normal readable path must not call recvfrom/drainSocket for this card
observeRawReceive() must not run
enqueuePacketForSession() must not run
sessionBoundaryPacketsDiscarded must not increase merely because new-session data arrived during HOLD
```

数据应留在 kernel socket backlog，直到 `complete(..., SUCCESS)` 先发布 RUNNING。

`complete(..., SUCCESS)` 后，HOLD 期间已经到达的同一批数据必须能够通过正常生产 receive/dispatch 路径被消费；不得通过“丢第一包/第一 trigger/前 N 包”实现边界。

### 3.3 begin fence 的 quiescence 顺序

`beginCardStartFence()` 是 Start 前最后一个 receiver-owned barrier。

必须保证：

1. 当前 card 已处于 ARMED 且 token 匹配；
2. 在 receiver thread 内先建立 HOLD 语义，使正常 receive loop 对该 card 不再执行 drain；
3. 在 hardware Start 尚未发送的前提下，对该 card 做最后一次显式 backlog quiescence 到 `WSAEWOULDBLOCK`；
4. 这次 quiescence 中读到的 packet 仍属于 Start 前 closed-admission 数据，只能走现有 boundary discard/closed 路径，不得进入 raw-order/processor；
5. quiescence 完成后到 `beginCardStartFence()` 返回之间再到达的 packet保持在 socket backlog，因为该 card 已处于 HOLD。

可以采用与上述等价的内部顺序，但必须能证明 begin 返回后不存在“该 card 仍会被 normal loop drain”的窗口。

### 3.4 receiver 主循环对 HOLD socket 的行为

不得让 HOLD socket 形成 readable busy-spin。

优先实现：

```text
build fdset 时跳过 START_FENCE_HOLD card
```

或等价机制，使 HOLD card 不触发普通 drain。

如果某个 receiver group 在当时没有任何可加入 readfds 的 socket，必须使用安全的 bounded wait/command wait 处理；不能构造无效的 empty Winsock `select()`，也不能无休止自旋。

不得修改现有 1 ms select timeout 作为本任务解决方案。

### 3.5 per-card 与 aggregate state

- card0 可以 RUNNING，而 card1~3 仍 ARMED/HOLD；
- 某卡进入 RUNNING 不能打开其它尚未完成 Start fence 的卡；
- controller 的 canonical measurement state 仍需在全部 target Start/fence 成功后才进入 RUNNING / `measurement_started`；
- aggregate receiver state 如继续导出，必须能够正确表达存在 HOLD 的情况，不得把 HOLD 误报为全局 RUNNING。

### 3.6 failure / rollback

至少覆盖：

```text
begin fence failure
Start send failure while HOLD
complete SUCCESS failure/timeout
complete FAILURE failure/timeout
3/4 partial Start rollback
```

本轮沿用现有 teardown/Fault 语义：发生 start transaction failure 后继续调用既有 rollback/Stop/disarm/reset 路径；若 teardown 本身失败，按现有 Fault 处理。

旧 token/fence 不得跨 session 复用。下一次 clean Start 必须从 PREPARING/ARMED 重新建立边界。

## 4. MeasurementSession transaction 要求

当前 transaction 是：

```text
sendStart(card)
-> on success commitStartFence(card)
```

本轮需要能够表达：

```text
begin fence(card)
-> sendStart(card)
-> complete fence(card, success/failure)
```

因此允许最小修改 `MeasurementSessionTransaction` callback contract。

推荐逻辑：

```text
for each card:
    if beginFence(card) fails:
        rollback

    sent = sendStart(card)

    if sent succeeds:
        if completeFence(card, SUCCESS) fails:
            rollback
    else:
        attempt completeFence(card, FAILURE)
        rollback
```

具体 Result reason/字段命名可按现有风格实现，但必须保留能区分 begin/send/complete 所在阶段的事实证据。

## 5. 软件边界说明

本任务保证的是软件能够定义和同步的 Start admission boundary。

当前 wire payload 没有 session epoch/generation tag，也没有本任务可使用的硬件 Start ACK。因此：

```text
若一个旧 session UDP datagram 在物理网络/driver 层直到新的 Start fence 完成以后才第一次到达 host socket，
仅凭现有 packet payload 无法绝对区分它与真正的新 session packet。
```

本轮不修改 FPGA/wire protocol，也不引入基于 triggerSeq 的新旧 session 推断。

现有 prepare/arm socket quiescence 与本轮 begin-fence 最终 quiescence共同用于缩小软件可控边界；不要把协议层不可区分问题混入本轮实现。

## 7. 本任务不采用的技术路径

不要用以下方式替代同步交接：

```text
Start success -> 原 CommitCard command -> 等下一轮自然生效
Start 前先把 card 设为 RUNNING
controller thread 单独 atomic-store RUNNING、但 receiver drain 与该 store 没有同一同步决策
send Start 后 sleep/yield/缩短 timeout
提高线程优先级来掩盖窗口
固定时间窗口
丢第一包/第一 trigger/前 N 包
根据 triggerSeq/packetSeq 猜 session
等待四卡全部 Start 后再全局开门
Start 期间暂停整个 receiver group/thread
```

同时不修改：

```text
FPGA packet/header/session protocol
NIC/MTU/SO_RCVBUF
receiver 数量/每 receiver 卡数
thread priority/affinity
select timeout
DataProcessor batch
PacketAssemblyBuffer reorder/basePacketSeq
Ring SHM/CUDA/ImagingSvc/FileSaver
日志时间窗
UI
P1 ingress/burst 优化
```

### T2 — deterministic Start-success / HOLD / readable / complete window

这是本轮核心测试。

必须构造：

```text
receiver card = ARMED
processor = ARMED

beginCardStartFence(token, card)
-> returns with card in HOLD

local Start sender returns SUCCESS
complete SUCCESS intentionally not yet applied

receiver receives execution opportunities while card remains HOLD
```

在 complete 前断言：

```text
these new-session datagrams have not been recv+dispatch+boundary-discarded by normal receiver path
socketPacketsReceived does not increase because of this held batch
processorPacketsDequeued does not increase
sessionBoundaryPacketsDiscarded does not increase because of this held batch
observeRawReceive has not established the new-session anchor
```

```text
completeCardStartFence(token, card, SUCCESS)
-> HOLD -> RUNNING
```

不重新发送前述 first-trigger datagrams；必须由之前已经 pending 的**同一批数据**随后通过生产 receive/dispatch 路径进入 processor，并组成完整 first trigger。

期望 delta：

```text
packetsDropped = 0
triggersPartial = 0
staleTriggerPacketsDiscarded = 0
first trigger complete = true
raw anchor belongs to this first admitted trigger
```

#### T2 测试实现方式

优先 Windows loopback UDP 集成测试：

- 使用真实 `MultiPortReceiver::run()` + production socket；
- HOLD 后把 first-trigger datagrams 发送到该 card UDP socket；
- 在 complete 前等待超过若干 receiver loop/select 周期，确认没有 recv；
- complete SUCCESS 后确认同一 backlog 被消费并完成 first trigger。

如果采用 deterministic decision seam：

- seam 必须由生产 `run()` 的 readable->drain 决策直接调用；
