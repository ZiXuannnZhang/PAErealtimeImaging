当前前端指标的实际含义：

| 前端名称 | 当前源码字段 | 实际含义 |

## 3. 应用日志修改

### 接收之前及控制流程

从监听启动前开始记录，不能等第一包到达后才启用：

- socket创建、绑定、非阻塞设置、实际接收缓冲大小、端口和错误码。
- 接收线程启动、优先级实际结果、首次进入接收循环。
- START／STOP请求、发送结果、每卡ACK接收时间及UI回调执行时间。
- prepareStart、completeStart、prepareStop、completeStop的进入、完成、状态变化。
- 任何组包状态清理的原因、卡号、触发号、已收包数和首包关联ID；尤其补齐当前completeStart清理路径的证据。
- 成像启动、停止、初始化、清队列和保存状态切换的起止时间，使用同一单调时钟关联。

这些都是观测点，不新增就绪后等待等控制行为。

### 接收循环与报文关联

保留现有逐包原始轨迹，增加完整循环记录：

- 循环开始到下一循环开始的完整间隔，覆盖统计和日志调用开销。
- select开始、结束、返回值、就绪端口集合。
- 每次socket drain的开始、结束、尝试次数、成功数、字节数、退出原因。
- 成功和失败的recvfrom时间、端口及错误码。
- 原始日志提交、统计回调、组包锁等待、组包处理、poll的耗时。
- 每个socket最近一次接收尝试、最近成功收包时间与循环进度。

修正当前成功recvfrom时序记录使用drain ID、后续才生成入口ID的关联问题：成功调用与原始报文共用同一个入口ID，drain ID另存，不混用。

### 最少干扰的记录方式

- 接收线程仅写固定大小二进制记录到预分配有界缓冲，不做JSON格式化、文件写入或系统命令调用。
- 从接收线程启动起保留最近5秒完整循环记录；应用入口连续2秒无采样数据后首次来包时，冻结此前5秒，并继续保留之后5秒。
- 该规则只生成接收突发段诊断标记，不改变session、清理组包或认定物理轮次。连续无采样数据按所有采集数据端口合并判断，ACK不算采样数据。
- 首次启动也使用相同机制；循环日志预算256MiB，既有原始轨迹预算保持不变。达到预算后显式标记不完整，不反压接收。
- 后台监测每100ms读取一次接收线程循环进度；超过20ms未推进时记录提示。该采样方式不能保证发现每一次20ms停顿，不得据此直接判为CPU抢占。
- 所有日志队列记录丢弃、预算耗尽、写入失败和导出完整性。

前端保留现有计数算法，仅将文案澄清为报文不完整触发和不完整触发缺包数。整触发未见数量在离线轮次报告中单列，避免引入实时跳号误判。

## 4. 接收侧系统抓取与分析工具

### 抓取方式

交付独立的启动／停止脚本，由用户在实机测试时运行；不在接收线程或GUI启动流程内自动提权。

使用本机已有的Pktmon和WPR。上一阶段仅核对过本机help和profiles，未执行系统抓取，不得据此声称抓取链路已验收。

- Pktmon只过滤采集卡IPv4、UDP及本机8000—8004端口；保留全部可观测组件与丢弃事件。实际命令以本机帮助为准，验证过滤器的组合语义，避免意外扩大到所有UDP流量。
- 每条报文截取128字节，保留网络头及采集协议前四字节，不抓取完整采样payload。
- 使用256MiB内存循环模式，避免采集时持续写入抓包文件。
- WPR使用内存模式的GeneralProfile；执行会话用短测试验证导出的事件是否包含线程调度、DPC／ISR相关证据。缺失时明确标记，不宣称已覆盖。
- 系统抓取从用户即将启动一轮物理触发前开始，应用检测到新接收突发段10秒后通知独立脚本停止；未检测到时30秒自动停止。
- 4000触发采集继续运行至结束，系统抓取不必覆盖整轮。

应用通过后台诊断控制通道发布带trialId、runId和单调时间的突发段通知；接收线程只向既有诊断缓冲提交事件，不等待脚本响应。脚本忽略早于本次抓取启动的通知。记录停止抓取及ETL落盘区间，因为此时I/O本身可能影响剩余采集。

启动脚本检查现有会话，禁止停止或覆盖不属于本任务的Pktmon／WPR会话。只清理本任务创建的过滤器。权限不足、工具冲突、启动失败、超时或输出缺失必须记录为失败，不能生成抓取成功的空报告。

### 导出与关联

诊断包增加系统抓取manifest，包含：

- trialId、应用runId、配置、过滤器、组件列表。
- QPC频率、QPC／应用单调时钟／UTC配对锚点。
- 每条命令、退出码、开始结束时间、输出文件大小和SHA256。
- ETW丢事件、循环覆盖及可观测层覆盖情况；无法获得的字段标记unknown。
- 原始ETL和转换结果均保留，应用导出失败时允许从manifest定位独立文件。

离线工具按源／目的地址、端口、触发号、包号和时间窗口关联应用与系统记录。Pktmon不同组件对同一包的重复观测不能累计为收到多个包。不能只用16位触发号关联跨轮或跨回绕记录。

报告给出以下判定：

| 证据 | 允许结论 |
|---|---|
| 应用入口有包，后续组包拒绝／清理 | 应用处理阶段有明确丢弃 |
| 系统某层有包，应用入口无包 | 缺失位于该观测层之后至应用入口之间，进一步结合丢弃与调度事件 |
| 系统与应用均有包，但应用时间明显滞后 | 存在交付／接收延迟，不能仅凭时间差确定具体层 |
| 最早可观测层也无包 | 原因未知，不能直接判采集卡、网卡或线路故障 |
| 轨迹丢记录、覆盖或时钟不可靠 | 相应区间无法判定 |
