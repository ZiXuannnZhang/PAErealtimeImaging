### 前端计数的确定性解释

packetsDropped 混合了两种口径：

- 旧触发切换时：期望包数减去去重后实收包数。
- 触发序号跳过时：跳过数量乘以期望包数。

见[DataProcessor.cpp:295](D:/ChatGPT/PAERealtimeImaging/CODEX_REPORTS/architecture-audit-20260909/latest/MC_410T_MultiCard/delivery/src/DataProcessor.cpp:295)和[DataProcessor.cpp:327](D:/ChatGPT/PAERealtimeImaging/CODEX_REPORTS/architecture-audit-20260909/latest/MC_410T_MultiCard/delivery/src/DataProcessor.cpp:327)。

因此20µs阶段约1.44万包并不等于约1.44万个经网卡确认丢失的数据报。其中超过99%来自整触发跳号推算。尤其卡1在23:27:00.458—23:27:02.914增加13,192包：该区间3个部分触发共缺32包，其余13,160＝470×28来自跳号。没有发送端触发/发包记录，无法判断这些跳过的触发是已发送而全丢，还是未产生对应数据报；不能断言这些推算全是真丢包，也不能断言是误报。

50µs会话也未清零旧的累计值：卡1从14,443增加至25,388，本阶段增量为10,945。前端瞬时 packetLossRate 根据相邻统计时刻的接收/缺包增量计算，部分触发延迟结算会改变显示时机。见[NetworkController.cpp:743](D:/ChatGPT/PAERealtimeImaging/CODEX_REPORTS/architecture-audit-20260909/latest/MC_410T_MultiCard/delivery/src/NetworkController.cpp:743)。这解释了数字口径，不解释入口断档的来源。

### 对性能与丢弃路径的核对

- 两阶段结束时，每卡 socketPacketsReceived、processorPacketsDequeued、packetsReceived 均相等；会话边界丢弃、迟到触发丢弃、组包越界、批次边界丢弃和保存队列丢弃计数均为0。入口同触发回退、跨触发迟到计数也为0。不能将本次现象认定为上述软件丢弃路径所致。
- 输入队列快照最高仅6包、保存队列最高1项。但快照大约2—3秒一次，不能证明采样间隙没有短暂积压。
- 50µs、block=50下，记录的成像块提交间隔约1.25秒，consumer累计平均处理时间约66—70ms。已输出的SHM观测中，忙槽覆盖、序号缺口、重复消费、通知不匹配均为0。没有证据支持“GPU处理来不及或SHM覆盖导致本次入口缺包”；这些观测也不能排除未测量的短时线程调度影响。
- 四卡共用“以太网3 / Realtek USB 10GbE Family Controller”，日志报告的实际接收链路速率是2.5Gbps。不能把设备名称中的10GbE当作本次协商速率。20µs到50µs的期望包数由28变70，负载为2.5倍，但增加负载与发生缺口的相关性不构成瓶颈定位。

## 4. 当前能定位到哪里

发送端实际触发/发包 → 传输与主机接收 → recvfrom/包头解析 → **入口序号断档已可见** → DataProcessor组包 → 实时重建。

“入口序号断档已可见”是观测边界，不是故障组件名称。附件没有逐包头、精确到达时刻、原始报文长度和发送侧记录；不能确定第一处发生偏差的位置。两个问题是否共享同一根因也无法确定。

上一轮发现的无界队列、逐socket排空、首到包定位、SHM单槽等仍是各自的架构风险，但此次证据不足以将任一项升级为这两次实机现象的已证实根因。

## 5. 最少缺失证据与停止点

继续根因定位需要补齐的是同一次故障的端到端证据，而不是更多同类累计日志：

1. 每个物理采集轮的开始标记，以及实际触发序号、时间、采集卡对应关系。用于准确识别“每轮首次”，以及解释511/34个推算跳号。
2. 故障触发在发送出口与主机接收侧的报文对照，至少包含card/IP、triggerSeq、packetSeq、报文长度、时间戳；记录捕获工具自身丢包情况。仅主机一侧抓不到某包，仍不能判定发送端没发。
3. 与同一故障对应的应用recvfrom入口逐包头或内存环形记录，用于比较“发送了什么、主机捕获了什么、程序实际读到了什么”。

这些证据可以一次小规模复现同时提供，不代表现在已选择某个修复方案。本次到此停止；没有部署、更改采集参数或修补产品。
