# 实时成像与采集保存链路隔离：测试报告

日期：2026-09-11

## 代码已验证

- Debug 完整默认目标构建通过：`build_mingw_debug.cmd`，包括主程序与 ImagingSvc。
- Release 完整默认目标构建通过：配置 `build/mingw_release` 后执行 `cmake --build build/mingw_release`。
- `imaging_bypass_test` 通过：验证 Disabled、ServiceNotReady、InvalidFrame、不完整帧、未启用通道、QueueFull、StaleSession、Stopping、队列深度和最大耗时统计。
- `data_processor_imaging_isolation_test` 通过：成像 worker 故意阻塞、容量 8 的队列饱和时连续提交 4000 帧，结果为 `saveAccepted=4000`；成像旁路按 QueueFull/QueueBusy 丢弃，回调抛异常时独立返回 CallbackFailed。
- `paimage_worker_checks` 通过：保存队列每卡上限、同步队列整块淘汰、session 切换，以及停止时 20 个已入队保存对象全部排空。
- `paimage_host_output_test` 通过：4 卡、20/50 微秒对应采样长度、float16 文件字节与显示/成像分支结果正确。
- `paimage_network_test` 通过：4 卡 loopback UDP、配置 ACK、20→50→20 微秒、启动过滤、保存文件和异步停止。
- `ring_block_assembler_test` 通过：沿用原有首触发/组块和角度规则。
- 测试工程完整构建后执行 `ctest --test-dir build/isolation_tests --output-on-failure`：27/27 通过，总耗时约 32 秒。
- 静态检查通过：保存 worker 与接收/SourceCore 文件不引用 `ImagingController`、`RingBlockAssembler` 或 `ImagingBypass`；成像旁路没有 sleep 等待服务。

## 压力测试已验证

软件压力已证明：在 4000 帧连续提交、成像 worker 延迟且队列持续满的条件下，保存接收结果保持 4000/4000；成像满队列不会等待或反压保存。该测试是进程内确定性压力，不代表外接网卡、驱动或磁盘的真机吞吐结论。

另执行 4 卡 loopback UDP、40 Hz、4000 次触发压力：

- 20 微秒：`hostRingReturns=16000`，测试通过，wall time 约 100.049 秒。
- 50 微秒：`hostRingReturns=16000`，测试通过，wall time 约 100.046 秒。

这两轮验证接收、SourceCore 和 host 输出在软件回放条件下完整交付 4×4000 卡帧；压力模式按既有测试设计关闭文件保存，因此不能替代真机“保存开”场景。

## 实机已验证

本执行环境没有连接任务书指定的采集卡、触发控制 FPGA、LabVIEW 和外接网卡，因此没有新增真机验证结论。既有程序的保存格式回归已由 loopback 和精确文件字节测试覆盖。

## 仍无法证明

- 同一笔记本、同一外接网卡、4001 个物理触发下，40 Hz、20 微秒和 50 微秒各条件的入口零丢包。
- 保存开/成像关、保存开/成像正常、成像延迟启动、成像服务停止四种真机组合。
- 单进程之外的 CPU、内存、调度、网卡驱动和进程级崩溃隔离。
- CUDA DLL 源码重编译未在本任务中执行；完整构建使用诊断 worktree 自带、哈希一致的预构建 CUDA DLL/导入库。
