# 最低生产条件启动零丢包与诊断日志时间窗导出执行回执

## 1. 结论与交付边界

已在隔离工作区完成本任务要求的两类改进：

1. 采集启动/停止改为由 NetworkController 统一拥有的 measurement-session transaction。所有 DataProcessor 完成本轮 prepare/reset 并明确 armed 后，才允许向采集卡发送 Start；四卡本地 sendto 必须全部成功才进入 RUNNING，部分成功会执行 best-effort Stop rollback 和 disarm/reset。
2. 诊断导出改为用户选择本机 local time 的 [startTime, endTime] 时间窗，跨 retention 中所有相交的 normal/active/incomplete run 导出，并保留明确标记的 boundary-before / boundary-after 上下文。活动 run 在点击导出时捕获 immutable boundary，后台线程负责 flush、扫描和打包。

本回执只证明源代码、Windows MinGW 构建、软件测试和 Ring 服务自测证据；没有把软件测试表述为实机已经零丢包。P1（40 Hz / 50 us 的稳态 burst 丢包）仍按任务要求留待下一轮时间窗日志分析。最终仍需在四卡生产条件 40 Hz / 20000 ns / 4 ns / A+B / 32 bit/channel / realtime imaging ON / 200 Aline 下执行多轮实机 Start/Stop 验收。

## 3. P0 session transaction 实现

新增 MeasurementSessionTransaction 小型 helper，用于把 prepare、arm、hardware start send、rollback 和 observer 事件绑定到一个实际 transaction。NetworkController 的 direct start 和 config/ready 后 queued start 都进入 executeStartTransaction()，没有保留第二条旧 gate 时序。

实际顺序为：

    DISARMED
      -> measurement_session_prepare
      -> 所有 DataProcessor worker prepare/reset 完成
      -> measurement_session_armed
      -> 所有 DataProcessor worker arm 完成
      -> measurement_start_command
      -> 四卡 doSendStartMeasure()
      -> 4/4 成功才 measurement_started / RUNNING

每个 processor 的 prepare/arm/disarm 通过 worker command queue 和 bounded wait 完成；GUI thread 不直接修改 worker 使用的 assembly buffer。prepare/disarm 会关闭 gate、更新 session token、清空 worker 内的 PacketAssemblyBuffer、清空旧输入队列、清除 m_lastFlushedTriggerSeq、m_hasFlushedOnce、m_consecutiveDiscards，并调用 CardStats::resetRawSequenceAnchor()。这些是生命周期边界清理，不增加当前 session 的 packetsDropped 或 triggersPartial，不会生成伪 partialTrigger。

arm 会再次确认旧包已排空后才打开 gate 和当前 token。DataProcessor 对 gate-off 或 token 不匹配的包进行边界丢弃计数，不进入当前 session 组包。首个有效 hardware trigger 因而不会与上一轮的 partial assembly、queue packet 或 raw-order anchor 混用。

四卡 start 只有 successCount == cardCount 且 failCount == 0 才成功。部分成功会记录 measurement_start_failed / measurement_start_rollback，对全部目标卡 best-effort Stop，再 disarm/reset 所有 processor，绝不静默进入 measuring。正常 Stop 先发送 hardware Stop，再 disarm/reset；Stop 本地发送失败会记录 measurement_stop_failed，并保留可重试的运行状态信息。

每个 session 使用稳定的 measurementSessionId，生命周期事件包含可取得的 configId、cardCount、successCount、failCount、dataTimeNs、dataTime、processRunId/runId、outcome/reason 以及 settings/runtime/card snapshot 关联字段。start、started、stop、stopped、rollback、failure 边界都会主动 requestFlush()；stop 完成后再做 bounded flush，磁盘 I/O 不进入 recvfrom/DataProcessor packet hot path。

## 4. 时间窗诊断导出实现

DiagnosticExportDialog 现在提供 local time 的可编辑开始/结束时间、现场说明和 ZIP 路径，显示当前 retention 的 earliest/latest coverage，并校验 start <= end、结束时间不晚于当前时间。用户不再先选择某个 run。

DiagnosticRecorder::captureTimeWindowRequest() 枚举 retention 下全部 run，选择与请求 [startTime, endTime] 相交的 normal、active 和 incomplete run。active run 在点击时先捕获 immutable export boundary 并执行必要 bounded flush；导出 worker 后续只读取该边界，点击之后新产生的 sequence 不会混入本次导出，之后仍按时间窗过滤。

事件类 events.jsonl/runtime.log 只保留正式窗口内记录。network_history、settings_history、card_history 逐行流式扫描，保留窗口内记录以及最后一条 timestamp <= startTime 的 boundary-before 和第一条 timestamp >= endTime 的 boundary-after context，并在输出中标记 windowRole=boundary-before/after。manifest 至少记录 requestedStartTime、requestedEndTime、exportCapturedAt、sourceRunIds、sourceRunCount、formal/context counts、实际首尾时间、active/incomplete 标志、缺失文件、截断原因和 recorder drop/write-error 状态。summary.txt 明确写出这是时间窗导出；无正式记录时返回明确 no-records 结果，不伪造当前空 run。
