# 采集卡误识别修复——可执行任务书

## 1. 任务目标

在当前接收侧系统诊断增强版本上修复动态采集卡发现逻辑。动态发现完成后，只有在本次发现会话中返回了 **60 字节 CONFIG 确认报文**的候选 IP 才能成为正式采集卡目标。ICMP、ARP、路由可达、18 字节就绪报文只能作为诊断证据，不能单独确认采集卡身份。

必须兼顾响应较慢的真实采集卡：发现过程使用有界、多轮、只重发未确认目标的策略；在整个发现窗口内持续接收晚到的 60 字节确认；不得因第一轮未及时响应就排除真实采集卡。

本任务完成后，应交付一个独立构建供用户在同一台式机和笔记本上实机验证。不得声称软件测试已经证明真实硬件发现成功。

## 5. 总体设计

实现独立的 CONFIG-ACK 动态发现组件，建议命名为 `PaimageCardDiscovery` 或 `CardDiscovery`。不要为了发现候选卡而构造完整的 `paimage::Backend`，因为完整后端会创建数据端口、处理器、保存器和接收线程，扩大改动面并污染正式采集状态。

发现流程分为四段：

1. 生成候选 IP，并枚举本机所有 IPv4。
2. 可选执行 ICMP/ARP 探测，仅记录可达性并用于安排发送顺序。
3. 对所有合法、非本机候选 IP 发送 CONFIG，分轮等待 60 字节反馈。
4. 将协议确认的 IP 按数值地址排序后交给现有 `startListeningWithIPs()`。

ICMP 未响应的地址仍必须进入 CONFIG 探测。真实采集卡是否响应 ICMP不能成为身份验证的前置条件。

## 6. 数据结构和接口

建议新增独立头文件和实现文件，例如：

- `delivery/include/PaimageAcquisition/CardDiscovery.h`
- `delivery/src/PaimageAcquisition/CardDiscovery.cpp`

建议的数据模型如下，名称可按项目风格调整：

```cpp
struct DiscoveryOptions {
    QString baseIP;
    int candidateCount = 32;
    QString localBindIP;
    int configDurationNs = 20000;
    int delayANs = 200;
    int delayBNs = 200;
    int ackWindowMs = 2000;
    int maxAttempts = 5;
    int finalGraceMs = 500;
    int icmpTimeoutMs = 150;
    QString discoveryId;
};

enum class DiscoveryCandidateState {
    Pending,
    ExcludedLocal,
    Invalid,
    SendFailed,
    Verified,
    TimedOut
};

struct DiscoveryCandidateEvidence {
    QString ip;
    DiscoveryCandidateState state;
    bool icmpReachable = false;
    bool arpReachable = false;
    bool ready18Observed = false;
    int attemptsSent = 0;
    int sendFailures = 0;
    int ack60Count = 0;
    int duplicateAck60Count = 0;
    qint64 firstSendNs = 0;
    qint64 lastSendNs = 0;
    qint64 firstAckNs = 0;
};

struct DiscoveryResult {
    QString discoveryId;
    QVector<QString> verifiedIPs;
    QVector<DiscoveryCandidateEvidence> candidates;
    QString localBindIP;
    QString error;
    bool cancelled = false;
};
```

发现 API 必须是有界、可在后台线程执行且资源自动释放的同步函数；由现有 `QtConcurrent`/`QFutureWatcher` 接回 UI。不要在 worker 线程访问 `MainWindow`、UI 控件或已销毁的 QObject。

## 7. 候选地址生成与本机地址排除

1. 沿用 `ScanBaseIP` 和 `ScanIPCount` 生成候选范围，保留 1–254 边界检查和数值顺序。
2. 使用 Windows 地址 API 枚举所有本机单播 IPv4。必须包含：
   - `up` 和 `down` 网卡；
   - 已断开但仍保留静态 IPv4 的网卡；
   - 用于采集的活动网卡地址；
   - 回环地址。
3. 候选地址与任一本机 IPv4 完全相同时标记为 `ExcludedLocal`，不发送 CONFIG。
4. 日志应记录对应接口的 index、LUID/GUID、名称、运行状态和本机地址；无法取得某字段时写 `unknown`，不得猜测。
5. ICMP 回复必须同时满足回复数量大于 0且 `ICMP_ECHO_REPLY::Status == IP_SUCCESS`。非成功状态只记诊断，不得标记可达。
6. 即使 ICMP 超时，候选地址仍进入 CONFIG 探测。

优先复用或提取现有 `NetworkDiagnostics` 中的只读接口枚举代码，避免维护两套 Windows 地址识别实现。

## 8. 本地发送接口选择

发现组件发送 CONFIG 时必须显式绑定本地 IPv4，与正式 `ControlSocket` 的要求一致：

1. `NetworkParams/LocalBindIP` 非空时，验证它确实属于本机；有效则使用。
2. 配置为空时，对扫描网段调用 `GetBestRoute2`，取得 Windows 选择的本地源 IPv4。
3. 结果必须是非零本机地址，且不能等于候选目标。
4. 无法获得可靠本地源地址时，发现失败并给出明确错误；不得静默使用 `INADDR_ANY`。
5. 记录选定接口及选择依据 `explicit` 或 `best_route`。

本次台式机的活动采集接口为 `192.168.0.100`。该事实用于验收对照，不得硬编码进程序。

## 9. CONFIG 探测和慢响应策略

CONFIG 命令使用现有 `paimage::configCommand(durationNs, delayA, delayB)` 生成，目标端口沿用正式控制链路的 `8080`。发现参数必须在点击“开始监听”时从 UI 取一次不可变快照；发现期间禁用相关参数控件。不得发送 START 或 STOP。

建议初始配置：

- `ackWindowMs = 2000`
- `maxAttempts = 5`
- `finalGraceMs = 500`
- 总发现等待上限约 `10.5 s`，另加很小的 socket 建立和发送开销

这些值通过 `QSettings` 暴露为诊断/网络配置项，并做合理边界限制，例如：

- `Discovery/AckWindowMs`：`500–5000`
- `Discovery/MaxAttempts`：`1–10`
- `Discovery/FinalGraceMs`：`0–2000`

发现算法：

1. 建立临时 UDP 反馈 socket，绑定 `INADDR_ANY:8000`，设为非阻塞并配置足够的接收缓冲。
2. 建立显式绑定本地接口的临时控制 socket。
3. 为本次发现生成唯一 `discoveryId`，清空临时接收队列并初始化每个候选状态。
4. 第 1 轮向所有非本机候选地址发送 CONFIG。UDP `sendto` 成功只代表本机协议栈接受发送，不能确认采集卡。
5. 在完整 `ackWindowMs` 内持续使用 `select`/非阻塞 `recvfrom` 排空反馈 socket。
6. 下一轮只向尚未收到合格 60 字节确认、且尚未达到发送上限的候选地址重发。
7. 达到最后一轮后仍等待完整 ACK 窗口，再等待 `finalGraceMs`，持续接受晚到确认。
8. 所有等待必须有绝对单调时钟截止时间；短暂 `select` 超时只是轮询，不代表候选失败。
9. 最终只有 `Verified` 候选进入结果；`SendFailed`、`TimedOut`、`ExcludedLocal` 等全部排除。
10. 对确认结果按 IPv4 数值排序并去重，保持卡号映射稳定。

不得因为已发现当前注册表中的 `m_nCards` 数量就提前结束。`m_nCards` 已经可能被误识别污染，不能作为动态发现真值。

## 10. 60 字节确认的接纳规则

一个反馈报文只有同时满足以下条件，才能确认采集卡：

- 本次发现临时 socket 实际收到；
- UDP 负载长度严格等于 60 字节；
- 源 IPv4 在本次候选列表中；
- 该候选不属于本机地址；
- 本次发现会话已经至少一次成功向该 IP 发送了 CONFIG；
- 报文到达时间位于首次成功发送之后、发现最终截止时间之前。

处理规则：

- 第一个合格 60 字节报文将候选标记为 `Verified`。
- 同一 IP 后续 60 字节报文只增加重复计数，不产生重复卡。
- 18 字节报文只记录 `ready18Observed=true`，不能确认卡。
- 其他长度记录并忽略。
- 来自非候选地址、本机地址或从未成功发送过 CONFIG 的 60 字节报文记录为 `unexpected_feedback` 并忽略。
- 当前协议没有已确认的事务号，无法严格区分同一 IP 的旧 CONFIG ACK 与本次 ACK。由于发现用途只验证该 IP 是否实现 CONFIG 响应，满足本次发送后的窗口约束即可；报告中必须如实记录这一协议限制。
- 如果后续能从硬件协议或真实报文中证明 ACK 存在固定头、回显字段或校验字段，再增加内容验证。本任务不得凭猜测发明报文字段。

## 11. socket 生命周期和并发约束

发现临时反馈 socket 与正式 `SocketReceiver` 都需要绑定端口 8000，因此必须严格串行：

1. 仅在 `m_isListening == false` 时启动发现。
2. 发现线程返回前，临时反馈 socket、控制 socket 和 WinSock 引用必须通过 RAII 完整关闭。
3. 主线程收到 `DiscoveryResult` 后才允许调用 `startListeningWithIPs()`。
4. 如果临时 8000 端口绑定失败，立即返回清晰错误和 WinSock 错误码，不得继续启动正式监听。
5. 窗口关闭、应用退出或用户取消时设置取消标志；发现循环在短轮询间隔内检查，关闭 socket并返回 `cancelled`。
6. 旧发现会话的回调不得覆盖新会话状态。主线程使用 `discoveryId`/generation 比对后再接纳结果。
7. 发现期间重复点击“开始监听”继续由 `m_scanning` 防抖。

## 12. MainWindow 接线修改

修改 `MainWindow::onStartListenClicked()` 的自动发现路径：

1. 保留 `--target-ips` 分支，继续直接调用 `startListeningWithIPs()`。
2. 自动模式不再调用 `scanReachableIPs()` 并把结果当作卡。
3. 构造不可变 `DiscoveryOptions`，后台调用 CONFIG-ACK 发现组件。
4. UI 文案分开显示：候选扫描、CONFIG 探测轮次、已协议确认卡数。
5. `DiscoveryResult.verifiedIPs` 为空时：恢复按钮、保持未监听，不修改 `m_nCards`，不保存错误卡数。
6. 非空时：明确记录每个已验证 IP 的 60 字节证据，再调用 `startListeningWithIPs(verifiedIPs)`。
7. `startListeningWithIPs()` 只接收“显式目标”或“CONFIG 已验证目标”。将日志来源从笼统的“网段扫描”细化为：
   - `explicit_target_ips`
   - `config_ack_discovery`
8. 只有 `config_ack_discovery` 成功后，才允许以验证列表长度更新并持久化 `m_nCards`。
9. 修复旧值污染：本次受测环境加载过 `NCards=5`。自动发现成功得到四卡后必须写回 4；发现失败时不得把旧值当作发现结果。

## 13. 正式配置阶段行为

发现 CONFIG 只用于身份确认。正式监听建立后，用户点击开始测量时仍按现有流程再次发送 CONFIG，并等待四卡正式确认，然后才发送 START。

原因：

- 正式 `paimage::ControlState` 需要建立自身 ACK 状态；发现状态不得偷渡到正式状态机。
- 重发同一组当前 UI 参数是幂等预期的一部分。
- 可以保留发现完成与正式测量之间的清晰边界和诊断证据。

不得把发现 ACK 直接写入正式 `ControlState::ack_`，也不得绕过正式配置确认。

## 14. 诊断日志要求

新增或完善以下结构化事件。所有事件携带 `discoveryId`、单调时间和有效配置值：

- `discovery.begin`：扫描范围、候选列表、本机 IPv4 列表、选定本地绑定地址、超时和重试参数。

## 16. 测试要求

### 16.1 纯状态机/传输替身测试

发现组件应支持注入时钟和传输替身，至少覆盖：

1. `.10` 同时是本机地址且 ICMP 成功：必须排除，CONFIG 发送次数为 0。
2. 普通主机 ICMP 成功但不返回 60 字节：最终不得成为采集卡。
3. 真实候选 ICMP 超时但返回 60 字节 CONFIG ACK：必须成为采集卡。
4. 第一轮超时、第三轮才返回 60 字节：必须被接纳，证明慢响应处理有效。
5. 同一 IP 重复返回多个 60 字节 ACK：结果只有一张卡，重复计数正确。
6. 只返回 18 字节 ready：不得确认采集卡。
7. 返回 59、61 或其他长度：不得确认采集卡。
8. 非候选 IP 返回 60 字节：记录并忽略。
9. 候选尚未成功发送 CONFIG 就收到 60 字节：记录并忽略。
10. 某候选 `sendto` 持续失败：达到上限后明确 `SendFailed`，其他候选不受影响。
11. 所有候选均超时：返回空列表，不能改变已有卡数。
12. `.2–.5` 以乱序确认：最终映射仍按 `.2,.3,.4,.5`。
13. 取消发生在等待中：及时退出、无 socket/线程泄漏。
14. 旧 `discoveryId` 的完成回调到达：不能覆盖新发现会话。

### 16.2 本机 socket 集成测试

使用独立测试夹具模拟不同源 IP 的候选，验证：

- CONFIG 只发到 8080；
- 反馈只从主机 8000 接收；
- 60 字节反馈源 IP 映射正确；
- 每轮只重发未确认候选；
