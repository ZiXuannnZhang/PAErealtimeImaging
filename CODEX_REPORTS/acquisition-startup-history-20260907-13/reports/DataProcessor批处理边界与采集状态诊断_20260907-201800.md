## 实施结果

### 批处理边界

修复前的条件表达式是：

~~~
while (m_inputQueue.try_dequeue(pkt) && count++ < PROC_BATCH_SIZE) {
~~~

当 count == 512 时，条件左侧仍会先 dequeue 第 513 个包，随后 quota 条件失败，包已经从队列中消失。现在生产线程和确定性测试共用 processInputBatch()，控制流为：

~~~
while (count < PROC_BATCH_SIZE && m_inputQueue.try_dequeue(pkt)) {
    ++count;
    ++processorPacketsDequeued;
    ++packetsReceived;
    // 原有测量门控、组包、丢包和分发逻辑
}
~~~

quota 在 dequeue 前检查，因此不存在“取出后仅因 batch 边界未进入处理”的路径；batchBoundaryDiscards 保留为防回归哨兵并在正常路径保持 0。PROC_BATCH_SIZE 仍为 512，没有增加队列容量或改变队列实现。

### 三个分层计数器

计数器位于 CardStats 和 CardStats::Snapshot，均为 std::atomic<uint64_t> 的累计值：

- socketPacketsReceived：MultiPortReceiver::run() 中 recvfrom() 返回且 recvd >= UDP_HEADER_BYTES、包头已解析、对应 DataProcessor 存在并即将 enqueuePacket(pkt) 时增加；短包、停止唤醒包和无 processor 不计数。
- processorPacketsDequeued：processInputBatch() 每次 m_inputQueue.try_dequeue(pkt) 成功后立即增加。
- batchBoundaryDiscards：表示“已 dequeue 但仅因 quota 未进入处理”的历史风险路径；修复后没有该路径，测试和运行均为 0。

既有 packetsReceived 仍在同一成功 dequeue/处理点增加；packetsDropped、triggersComplete、triggersPartial、triggersDiscarded、saveQueueDiscards 以及队列深度和速率字段均保留，未用新字段替换旧语义。
