让下一次30微秒、40Hz、4001次物理触发实验能获得：

1. 完整的应用入口逐包证据、各轮启动前后接收循环证据。
2. 可核实的系统抓取状态，明确区分未启动、失败、运行中、已抓取、已验证。
3. Pktmon网络层与应用入口可关联的报文记录，WPR调度证据单独说明覆盖能力。
4. 一次导出同时包含应用日志、系统抓取状态及已完成的系统文件，避免用户漏交。
5. 无管理员权限也能自动完成软件交付与负向验证；真实系统抓取未验证必须保留为独立验收项。

### 已检查到的实现缺陷，必须修复

- 启动脚本未检查每条过滤器添加命令的退出码，不能证明实际过滤集合正确。
- 正常启动后的状态文件直到等待结束才写，运行中没有可靠的ready握手，手动停止也可能找不到状态文件。
- 状态判断依赖有限的本地化文本，工具错误容易被误称为已有会话；需区分unknown、command_failed、busy。
- 脚本清理调用整体filter remove，不能保证只删除自己的过滤器；不能根据“启动时为空”推断“停止时仍只有自己的”。
- 手动停止与自动停止缺少互斥、幂等和当前会话身份验证，旧状态文件可能误停新会话。
- 通知只有notifiedWallMs的时间过滤，可能把抓取之前已发生、但延后通知的burst关联到本轮；必须验证burst本身的时间。
- 仅检查输出非空或转换退出码，不能证明里面存在目标UDP、有效协议头、时间窗口或调度事件。
- 应用没有显示系统ready/failed，也没有自动打包系统结果；操作完全依赖独立命令和人工提交目录。

### 步骤二：修复循环日志，保留各轮窗口

保留现有逐包trace和timing接口兼容性。增加独立的窗口记录模式，不更改采集处理时序。

- 接收线程只向预分配有界队列提交固定记录；文件写入、格式化、冻结复制均在后台。
- 后台维护64MiB、最长5秒的滚动窗口。超过容量先淘汰最早记录，并记录actualCoverageStart和preWindowTruncated；容量不是时间覆盖保证。
- 连续2秒无采样后的首包沿用BurstMark，只作为观测标记，不改变session或清队列。BurstMark冻结前5秒并保留后5秒。
- 首包在监听启动不足2秒时也生成首次窗口，明确beforeListenerStart，不伪造前5秒覆盖。
- 窗口重叠时合并存储并记录多个burst ID；记录序号仅存一次，窗口索引引用区间。
- 累计冻结窗口文件预算256MiB；已保存窗口不覆盖。达到预算后标记新窗口未完整保留，继续接收。后台滚动监测可继续。
- 无burst时不持续把全监听期循环写到磁盘；另存每秒聚合、生命周期和控制事件。
- 修复字节预算尾余量；每条记录最终归类为写入、队列丢弃、预算省略或待处理。正常滚动淘汰单列retentionEvicted，不冒充日志错误；记录守恒按定义可验证。
- 窗口完整性与全局完整性分开。主动保留窗口以外的记录缺口不得被旧分析器误判成丢包；新增schema版本并保留旧schema读取。

完成判据：小预算、80字节非整倍数预算、重复轮次、窗口重叠、无burst、导出中途和写失败测试通过；接收不等待日志消费者。

### 步骤三：将系统抓取改成受控状态机

保留兼容旧脚本入口，新主入口为start_system_capture_admin.ps1及stop_system_capture_admin.ps1。新增外部命令适配层供确定性测试替换；默认调用真实工具，模拟结果存verification/synthetic并标simulation=true。

状态：idle → preflight → starting → ready → collecting → stopping → validating → complete；任一步可进入failed，另有partial、unsupported、skipped。无目标数据为no_target_packets，不能算有效试验。

- 从启动前即原子写capture-state.json，每次转移先写状态和已取得资源。使用临时文件＋同目录替换，读端容忍短暂重试。
- trialId自动生成为时间＋UUID，runId、listenId、measurement session和trialId各自独立；不把同监听多轮的session假定为递增。
- 输出目录必须新建或属于同一session token的续做，拒绝复用其他轮文件。
- 工具适配器每条命令记录参数数组、退出码、stdout、stderr、超时、UTC和QPC起止。退出码成功且状态可识别才推进；未知输出不当作busy或成功。
- 支持本机已观察到的中英文状态，保留样本做解析测试。优先结构化查询；无结构化接口时保守标unknown并退出，不使用猜测性正则放行。
- 每次filter add成功后再登记归属；全部添加后读取实际过滤器集合，比对IP、UDP和端口。
- 必须同时限定采集卡IP及8000—8004端口，空CardIPs不默认扩大抓取，改为从应用请求配置取得；仍为空即失败。
- ready只有在Pktmon和默认要求的WPR均启动、状态查询确认、应用握手匹配后发布；显示“可开始物理触发”，不声称已经有可分析证据。
- --NoWpr仅供明确选择的降级模式；报告captureMode=pktmon-only、wpr=skipped_by_operator，不自动把WPR失败当成功降级。
- 启动后等待最多60秒；匹配新burst后10秒停止。通知必须同时满足runId、trialId、capture session token和burstMonotonicNs不早于ready边界。旧burst的延后通知不得触发本轮停止。
- 自动停止与人工停止共用互斥和幂等函数；最终状态重复stop只返回原结果。
- 只有仍能核实当前活动会话属于本session token时才发全局stop。归属不明时标ownership_unknown，不停止外部会话。
- 清理优先逐名删除本任务过滤器；本机不支持逐名删除时，仅在重新确认完整过滤集合与本任务一致后允许整体删除，否则留存并报告，不擅删。
- 用try/finally保证中途失败留下状态及资源归属；进程崩溃后恢复也需重新核实归属，不凭旧布尔字段盲目stop。

Pktmon默认all组件、flow/drop、截取128字节、256MiB内存模式；WPR默认GeneralProfile内存模式。用本机help验证参数，不安装驱动，不改网卡配置。

### 步骤五：停止、转换和真正的数据验收

停止时先更新状态，再停止所属会话并等待文件落盘。记录停止/转换I/O区间，不能把该阶段抖动混入无抓取干扰的对照。

- 保存原始Pktmon ETL、PcapNG、保留组件/丢弃信息的文本或结构化结果、WPR ETL；不要只留转换后的PcapNG。
- drop-only结果可以合法包含0个丢弃事件，不能因为无drop就判失败；要求命令执行成功和结果可解析，而非必须存在丢弃。
- 非空ETL或转换成功不等于抓取有效。解析至少一个目标UDP头、触发/包号，核实过滤地址、时间范围及实际记录数。
- 报告每个组件、方向、包实例计数；同一包经过多组件的记录去重用于唯一包统计，同时保留分层路径。不能把同层真正重复UDP误合并为一个报文。
- WPR验证是否确实有目标接收线程及调度事件，DPC/ISR独立记录present/absent/unknown。不自行从空输出推断无调度问题。
- 保存ETW丢事件、缓冲覆盖证据；无法获取时写unknown。只有覆盖窗口、时钟和丢记录情况足够可靠时，才允许使用系统未见的否定证据。
- manifest分离commandSuccess、artifactValid、targetPacketsPresent、timeCoverage、lossStatus、layerCoverage及analysisReady。complete仅表示流程完成，不等于所有层可下结论。

### 步骤六：统一离线分析与必要的新检测项

新增startup_diagnostics_analyze.py，复用原解析器，接受application-zip、system-capture（ZIP已含时可省略）、rounds-json和output。支持旧原始trace、新窗口schema及现有应用包，不重写已有可靠的包完整性算法。

新增检测项：

1. 采集轮首号、首个有效号、首个可见号分别记录；物理4001由用户声明，不从入口首号推导。
2. 每包关联ingress ID、源/目的地址端口、触发号、包号和长度；输出首触发到后续触发的网络观测间隔和应用取包间隔。
3. 每轮四卡起始缺号是否一致、首段缺包区间、后续25ms节奏及长短间隔配对。
4. 控制/清理/入队丢弃发生在入口前后哪个区间；应用入口全缺与后处理丢弃分别统计。
5. 每秒诊断线程写盘量、日志队列峰值、接收循环最大间隔；标记ETL停止落盘区间以识别诊断本身干扰。
6. 显式保存steady-clock、QPC和UTC配对锚点。各事件边界采用相邻QPC采样包围，保存配对误差上界；硬件时钟不可直接与QPC相减。

判定矩阵：

|证据|允许结论|
|---|---|
|应用入口有包，源状态机随后丢弃|定位到明确的程序处理路径|
|系统某层有包，应用无包，双方覆盖可靠|限定在该观测层到应用记录之间，不能自动指认socket队列|
|系统/应用均有，应用明显滞后且时钟可靠|报告观测层到应用延迟，不能称UDP排队时间|
|最早可观测层无包|该层未见，硬件/驱动/更早环节未知|
|抓取缺失、损坏、覆盖不全或时钟未知|不作否定归因|

不得按跨轮16位触发号单独关联；保留同一触发号不同packet instance。分析器不把没有保存的轮次判为存储丢包。

### 步骤七：可选socket网络时间戳，不阻塞核心交付

该项定位为独立实验能力，默认off，不能替代Pktmon正向验收。

- 日志off/on同一输入保存数据及组包结果一致。没有额外输入缺包才可称该回放通过；不规定虚假的精确性能提升。
- 统一ZIP导出：应用+失败状态、应用+成功合成系统产物、进行中、文件缺失、同名trial冲突。

## 6. 用户实机操作卡的最终流程

固定30微秒、40Hz、block=50、bypass、socket timestamp off、相同保存和成像状态。每轮4001物理触发，含1次多余首触发。

1. 启动独立新构建，先进行一次普通应用日志对照，保存到新目录。
2. 在应用选择准备系统抓取，自动生成trial与请求文件。
3. 用户显式运行管理员入口，应用显示ready后再发物理触发。ready失败则这是应用日志轮，不能标作系统试验。
4. 触发后约10秒自动停止系统抓取；程序继续完成约100秒采集。任何时候都不等待用户回答来关闭抓取。
5. 结束后一次导出包含应用和系统文件的诊断ZIP，摘要显示目标包数、时间覆盖和缺失项。
6. 不要求用户手写复杂命令或手动拼接多个目录；备用命令写在操作卡附录。

没有系统ready或管理员环境时，不要求重复物理试验来“碰碰运气”；先保留失败状态用于分析。

## 7. 最终交付与验收边界

交付目录包含：bin可运行Release、diagnostic-tools脚本及分析器、schemas、verification、操作卡、实现报告、artifact-manifest和SHA256。产物不必强行提交Git中被忽略的二进制；源码、测试、schema和文档提交新分支，工作树干净，产物用manifest关联源码提交。

最终报告按以下三项分别给状态：

- 软件实现与自动测试：passed/failed，列具体证据。
- 本机真实系统抓取：verified/not_verified/failed，说明权限与环境。
- Realtek实机分层抓取：awaiting_user_test，除非确实拿到对应实机证据。

“软件交付完成、管理员正向抓取待验收”是允许的无人值守交付状态；“所有诊断目标均完成”不是。不得以权限不足为由漏做状态机、模拟测试、打包或操作卡，也不得以任务完成压力虚构真实ETL。

收尾记录新worktree、分支、提交、EXE绝对路径及hash，说明与原采集路径的行为差异（默认仅诊断）。不要运行原有长测、打开GUI、改硬件或自行继续采集修复。
